# Task: pos — Proof of Storage engine (β)

Module: `crates/syncback-core/src/pos/`
Files: `mod.rs` + `tests.rs`

---

## Overview

The PoS engine contains the pure logic for Proof-of-Storage challenge-response. It is
stateless — callers (BackupCoordinator, RepairAgent, daemon scheduler) pass all inputs
explicitly and feed results into TrustEngine.

**Phase 1 gate requirement:** `challenge → response → verify на лету` (on-the-fly
verification from local source data, no stored expected values in DB).

### What this module does

1. **Challenge selection** — given a `SymbolPlacement`, pick which ESI to challenge for a
   specific holder. Deterministic selection keyed by nonce (no stored challenge state needed).

2. **Response verification** — given a holder's response (bound symbol bytes for a
   challenged ESI), verify it by re-encoding from the local source block and comparing.
   No hashes are stored; the encoder re-derives the expected bytes on the fly.

3. **Adaptive frequency** — compute how many challenges to issue per holder per week based
   on symbol volume and current trust score.

4. **Scheduling** — given a list of placements and their `last_verified` timestamps, return
   which ones are due for a challenge this cycle.

5. **Result classification** — classify a completed round (pass/fail/timeout) into the
   enum the daemon uses to call `TrustEngine::record_pos_result`.

This module has **no DB dependency**. It does not touch `redb`. The caller reads
`SymbolPlacement` from DB, calls PoS engine functions, and writes the result back to DB
and TrustEngine.

## Types

Define within `pos/mod.rs`:

```rust
/// A single PoS challenge issued by the owner to one holder.
/// Sent over the wire as part of PosChallenge message.
#[derive(Debug, Clone, PartialEq, serde::Serialize, serde::Deserialize)]
pub struct PosChallenge {
    /// Unique challenge identifier (random 16 bytes, generated by caller).
    pub challenge_id: [u8; 16],
    /// Which source block this challenge is for.
    pub source_block_id: SourceBlockId,
    /// Which ESI the holder must return data for.
    pub esi: u32,
    /// Timestamp when challenge was issued (for timeout tracking).
    pub issued_at: Timestamp,
}

/// A holder's response to a PoS challenge.
/// Received from the wire.
#[derive(Debug, Clone, PartialEq, serde::Serialize, serde::Deserialize)]
pub struct PosResponse {
    /// Must match PosChallenge.challenge_id.
    pub challenge_id: [u8; 16],
    /// The ESI that was challenged.
    pub esi: u32,
    /// Bound symbol data (exactly T bytes = ErasureParams.t).
    /// This is the per-holder-bound version (NOT raw RaptorQ output).
    pub data: Vec<u8>,
}

/// Outcome of verifying a PoS response.
#[derive(Debug, Clone, PartialEq)]
pub enum VerifyOutcome {
    /// Response data matches re-encoded expected bytes.
    Pass,
    /// Response data does not match (holder corrupted or lost the symbol).
    Fail { esi: u32 },
    /// Response was not received before the deadline (7 days).
    Timeout,
}

/// One holder's challenge schedule entry.
#[derive(Debug, Clone)]
pub struct ChallengeScheduleEntry {
    pub holder_id: IdentityPub,
    pub source_block_id: SourceBlockId,
    /// How many challenges to issue this week for this holder.
    pub challenges_due: u32,
    /// Candidate ESIs the caller can select from (computed from esi_ranges).
    pub available_esis: Vec<u32>,
}

/// Error type for PoS engine operations.
#[derive(Debug, thiserror::Error)]
pub enum PosError {
    /// Placement has no ESI ranges (no symbols assigned yet).
    #[error("placement has no ESIs: source_block={0}")]
    NoEsis(SourceBlockId),

    /// Erasure encoder failed to re-encode for verification.
    #[error("encode failed during verification: {0}")]
    EncodeFailed(#[from] crate::erasure::ErasureError),

    /// Response data length does not match expected symbol size.
    #[error("response data length {got} != expected {expected}")]
    ResponseSizeMismatch { expected: usize, got: usize },
}
```

## Public API

```rust
/// Select the ESI to challenge for a given placement.
///
/// Selection is deterministic given (source_block_id, holder_id, nonce):
/// index = fnv1a_32(source_block_id.0 || holder_id.0 || nonce.to_le_bytes())
///         % total_esi_count(placement.esi_ranges)
/// then map index → concrete ESI from esi_ranges.
///
/// `nonce` should be fresh per challenge (e.g., incrementing u64 or random).
/// Returns Err(NoEsis) if placement has no ESI ranges or zero total symbols.
pub fn select_challenge_esi(
    placement: &SymbolPlacement,
    nonce: u64,
) -> Result<u32, PosError>;

/// Verify a holder's PoS response by re-encoding from local source data.
///
/// Calls encoder.encode(source_block, params, response.esi, 1, block_id, holder_id)
/// and compares the resulting bound symbol data byte-for-byte with response.data.
///
/// Returns:
///   Ok(Pass)              — data matches
///   Ok(Fail { esi })      — data does not match
///   Err(EncodeFailed)     — encoder error (internal, treat as transient)
///   Err(ResponseSizeMismatch) — response.data.len() != params.t as usize
///
/// The source_block must already be encrypted (same bytes that were encoded
/// when the symbols were originally created). Caller is responsible for
/// reading and decrypting nothing — the source block here is the encrypted
/// blob as stored on disk, before erasure encoding.
pub fn verify_response(
    response: &PosResponse,
    source_block: &[u8],
    params: &ErasureParams,
    block_id: &SourceBlockId,
    holder_id: &IdentityPub,
    encoder: &dyn ErasureEncoder,
) -> Result<VerifyOutcome, PosError>;

/// Compute how many challenges to issue per week for one holder.
///
/// Formula (from docs/beta/raptorq_cheatsheet.md):
///   volume_factor = ceil(symbol_count / POS_VOLUME_DIVISOR)   // POS_VOLUME_DIVISOR = 1000
///   trust_factor  = 2.0 - trust_score                         // range [1.0, 2.0] for trust in [0, 1]
///   challenges_per_week = POS_BASE_CHALLENGES_PER_WEEK * volume_factor * trust_factor
///                                                             // rounded up to nearest u32
///
/// symbol_count: total symbols this holder stores (placement.symbol_count()).
/// trust_score: combined trust in [0.0, 1.0] (from TrustEngine::combined_score).
///
/// Result is always >= POS_BASE_CHALLENGES_PER_WEEK (minimum 1).
pub fn challenges_per_week(symbol_count: u32, trust_score: f64) -> u32;

/// Given a list of placements and their hot-cache last_pos timestamps, return
/// the subset that are due for a challenge this cycle.
///
/// A placement is due if:
///   last_verified.is_none()
///   OR now.0 - last_verified.0 >= secs_per_challenge_interval(challenges_per_week_for_this_holder)
///
/// Where secs_per_challenge_interval = SECS_PER_WEEK / challenges_per_week.
///
/// Returns one ChallengeScheduleEntry per due placement.
/// Entries with no available ESIs (esi_ranges empty) are silently skipped.
///
/// trust_fn: closure to look up trust score for a holder — typically wraps
/// TrustEngine::combined_score. Takes IdentityPub, returns f64 in [0.0, 1.0].
pub fn due_challenges<F>(
    placements: &[SymbolPlacement],
    last_verified: &[(SourceBlockId, IdentityPub, Option<Timestamp>)],
    now: Timestamp,
    trust_fn: F,
) -> Vec<ChallengeScheduleEntry>
where
    F: Fn(&IdentityPub) -> f64;

/// Check if a challenge has timed out.
///
/// Returns true if now.0 - challenge.issued_at.0 >= POS_TIMEOUT_SECS (7 days).
pub fn is_timed_out(challenge: &PosChallenge, now: Timestamp) -> bool;

/// Classify a completed PoS result for one holder into a PosOutcome
/// ready to pass to TrustEngine::record_pos_result.
///
/// Each call represents one challenge that was either passed, failed, or timed out.
/// Timeout counts as a challenged-but-not-passed event (challenged=1, passed=0).
///
/// week_number: monotonically increasing protocol week number (caller tracks this).
pub fn outcome_from_verify(
    result: &VerifyOutcome,
    week_number: u32,
) -> PosOutcome;
```

## Business Rules

### Challenge selection: deterministic from nonce

```
select_challenge_esi(placement, nonce):
  total = sum of all counts in placement.esi_ranges
  if total == 0: return Err(NoEsis)

  // Mix source_block_id + holder_id + nonce to get index
  hash_input = source_block_id.0 (32 bytes)
             || holder_id.0 (32 bytes)
             || nonce.to_le_bytes() (8 bytes)
  h = fnv1a_32(hash_input)
  index = h % total

  // Walk esi_ranges to find the concrete ESI at position `index`
  for (start, count) in placement.esi_ranges:
    if index < count: return Ok(start + index)
    index -= count

  // unreachable if total is correct
```

FNV-1a 32-bit is chosen for its simplicity (no external dependency):
```
fnv1a_32(bytes):
  hash = 2166136261u32  // FNV offset basis
  for byte in bytes:
    hash ^= byte as u32
    hash = hash.wrapping_mul(16777619u32)  // FNV prime
  hash
```

This is pure selection logic. The caller generates the nonce (e.g., incrementing per
challenge issued, or random). The determinism property means that given the same placement
and nonce, the same ESI is always selected — useful for deduplication if the challenge
must be re-issued.

### Verification: on-the-fly re-encode

```
verify_response(response, source_block, params, block_id, holder_id, encoder):
  if response.data.len() != params.t as usize:
    return Err(ResponseSizeMismatch)

  expected_symbols = encoder.encode(
      source_block, params,
      start_esi = response.esi,
      count = 1,
      block_id, holder_id
  )?

  expected = &expected_symbols[0].data

  if response.data == expected:
    return Ok(Pass)
  else:
    return Ok(Fail { esi: response.esi })
```

No hashes are stored anywhere. The expected value is derived purely from source data.
The source_block passed in must be the encrypted source block exactly as it was when
symbols were originally encoded (i.e., compress → encrypt → this bytes → encode).

### Adaptive challenge frequency

```
volume_factor = (symbol_count + POS_VOLUME_DIVISOR - 1) / POS_VOLUME_DIVISOR
              = ceil(symbol_count / POS_VOLUME_DIVISOR)

trust_factor  = 2.0 - trust_score.clamp(0.0, 1.0)
              // trust=1.0 → factor=1.0 (minimum, trusted holder)
              // trust=0.0 → factor=2.0 (maximum, untrusted holder)

challenges_per_week = max(
    POS_BASE_CHALLENGES_PER_WEEK,
    ceil(POS_BASE_CHALLENGES_PER_WEEK as f64 * volume_factor as f64 * trust_factor)
)
```

Constants from `constants.rs`:
- `POS_BASE_CHALLENGES_PER_WEEK = 1`
- `POS_VOLUME_DIVISOR = 1000`

Examples:
- 500 symbols, trust=0.8: volume_factor=1, trust_factor=1.2, result=2
- 1500 symbols, trust=0.5: volume_factor=2, trust_factor=1.5, result=3
- 500 symbols, trust=1.0: volume_factor=1, trust_factor=1.0, result=1
- 2500 symbols, trust=0.0: volume_factor=3, trust_factor=2.0, result=6

### Scheduling: which placements are due

```
secs_per_challenge_interval(cpw) = SECS_PER_WEEK / cpw

A placement (block_id, holder_id) is due if:
  last_verified is None
  OR now.0 - last_verified.0 >= secs_per_challenge_interval(cpw)

Where cpw = challenges_per_week(placement.symbol_count(), trust_fn(&holder_id))
```

Only `Alive` placements should be passed in by the caller (non-Alive placements are
logically excluded from PoS). The function itself does not filter by status — the caller
does this DB-side.

### Timeout rule

```
is_timed_out(challenge, now):
  return now.0.saturating_sub(challenge.issued_at.0) >= POS_TIMEOUT_SECS
```

`POS_TIMEOUT_SECS = 7 * 24 * 3600 = 604800` (from `constants.rs`).

### TrustEngine outcome mapping

```
outcome_from_verify(result, week_number):
  match result:
    Pass    → PosOutcome { week_number, challenged: 1, passed: 1 }
    Fail    → PosOutcome { week_number, challenged: 1, passed: 0 }
    Timeout → PosOutcome { week_number, challenged: 1, passed: 0 }
```

Both `Fail` and `Timeout` count as 1 challenged, 0 passed. The distinction between
them matters for the daemon's repair logic (Fail = possible corruption = trigger repair
and send storage_warning; Timeout = holder offline = lower P but no repair trigger),
but for trust scoring purposes both are treated equally.

## DB Operations

This module has **no DB dependency**. It is pure logic.

The caller (daemon coordinator) is responsible for:
1. Reading `SymbolPlacement` records from `Db::list_placements_for_owner` (or equivalent)
2. Reading `PlacementAgg.last_pos` from the hot cache
3. Calling `pos::due_challenges(...)` to get the list
4. Issuing challenges over the network
5. Receiving responses over the network
6. Calling `pos::verify_response(...)` to verify
7. Writing `SymbolPlacement.last_verified` back to DB
8. Calling `TrustEngine::record_pos_result` with the `PosOutcome`

## Notes for implementer

- `select_challenge_esi` uses FNV-1a 32-bit — no external crate needed. Implement inline.
  The point is determinism and simplicity, not cryptographic strength.

- `verify_response` calls `encoder.encode(source_block, params, esi, 1, block_id, holder_id)`.
  This re-creates the full RaptorQ intermediate representation internally (O(K) work). For
  Phase 1 this is fine — the verify call is rare (once per week per holder). If this becomes
  a bottleneck in future, the encoder can be extended with a faster single-symbol path.

- The `source_block` parameter in `verify_response` is the **encrypted** source block as it
  existed when encoding happened. The caller must read it from disk (same file that was
  backed up). If the file was deleted (LocalState::Deleted), the caller should not call
  this function — instead record a PoS skip and let the repair/cleanup flow handle it.

- `due_challenges` receives `last_verified` as a separate slice (not embedded in
  `SymbolPlacement`) because the hot cache (`PlacementAgg.last_pos`) may differ from
  the warm DB value. The caller passes whichever is authoritative (hot cache is
  preferred at runtime; cold scan at startup).

- Tests use `RaptorQEncoder` directly (not a mock). Phase 1 test data should use a small
  source block (1–2 symbols worth of data) to keep test runtime fast.

- All tests in `pos/tests.rs`, never inline. See CLAUDE.md.
