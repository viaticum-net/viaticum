Disk pressure + eviction = data loss для владельца\n\nEviction priority: `importance × trust_of_owner × (1 + age_bonus)`. Высокий возраст файла → age_bonus растёт → файл чаще остаётся. Но \"важность\" задаётся владельцем. Холдер evict файлы с низким `importance × trust`.\n\nРеальный сценарий: пользователь X даёт low importance видеоархиву (reasonable: это не документы). Его партнёры испытывают disk pressure. Все видео вытесняются одновременно у нескольких партнёров. Если это случилось быстрее, чем repair успел сработать — данные потеряны. Именно correlation risk: disk pressure у партнёров коррелирует (все купили дешёвые 500 ГБ диски, все заполнились примерно одновременно).\n\nВ симуляциях это не тестировалось — эксперименты 23-27 тестировали механизм eviction, не корреляцию дисковых событий между пирами.\n\n### 1.5. PoS = stub в alpha, но beta зависит от него для trust\n\nВ плане β указано: \"PoS SendPosChallenge — реальная реализация (сейчас stub)\". Весь trust engine тестируется с заглушкой вместо реального механизма.\n\n### 1.6. Chunk restore для файлов >32 МБ — тоже в β.4\n\nAlpha не умеет восстанавливать файлы больше 32 МБ. Это не edge case — это типичное фото RAW (25-50 МБ), видео, любой ISO. Система позиционируется как \"личный бекап фото и документов 30-160 ГБ\", но не умеет восстанавливать фото RAW прямо сейчас. И это исправление запланировано на последнюю фазу бета.\n\n---\n\n## 2. Что over-engineered\n\n### 2.1. RaptorQ в beta — преждевременная оптимизация\n\nRS работает. E2E тесты проходят. Какие assumptions ошибочны\n\n### 3.1. \"I-компонент нельзя ускорить — время неподделываемо\"\n\nЭто верно для глобальных атак. Но для индивидуального участника: я запускаю несколько нод (Sybil), каждая накапливает I параллельно. Через 26 недель у меня есть 10 нод с хорошим I-score. Документ отвечает на это \"Sybil через subnet limit\" — но subnet limit нет в alpha, и в бета он тоже нигде явно не запланирован.\n\nДаже без Sybil: I = cumulative mean GB·days. Если я плохой партнёр (держу мало для других), мой I растёт медленно. Но он растёт — просто медленно. \"Время неподделываемо\" правда, но это не anti-Sybil, это anti-churn.\n\n### 3.2. \"Конкурент — это 'ничего', не AWS\"\n\nЭто рационализация, а не анализ рынка. Реальный конкурент сейчас — iCloud/Google Photos для фото (бесплатно до 15-100 ГБ), и \"жёсткий диск в ящике стола\" для архивов. SyncBack требует: установить daemon, ввести seed phrase, найти партнёров, ждать 4-13 недель до полного escrow. iCloud требует: залогиниться.\n\nПозиция \"98% надёжности лучше чем 0%\" игнорирует что у целевого пользователя уже есть iCloud с 99.99% надёжностью по подписке $3/мес. Вопрос не \"лучше ли это чем ничего\", а \"лучше ли это чем $36/год без геморроя\".\n\n### 3.3. \"Cold backup снимает churn/repair/NAT проблемы\"\n\nЧастично верно, но: холодный бекап не снимает проблему bootstrap. Пользователь должен быть online и отвечать на PoS раз в неделю. \"Ноутбук закрыт — подождём\" работает для restore. Но если ноутбук закрыт 2 недели — PoS не отвечен — trust падает у всех партнёров. Это не churn (уход из сети), это обычная offline-жизнь реального пользователя.\n\n7-дневный PoS timeout предполагает что за 7 дней нода хотя бы раз выйдет в онлайн. Это разумно, но не гарантировано (отпуск, командировка, сломан роутер). При пропуске PoS P-компонент ухудшается у ВСЕХ партнёров данной ноды. Мягкость восстановления (4-week rolling) означает что один пропущенный PoS раунд влияет на trust 4 недели.\n\n### 3.4. \"GB·days как валюта работает без токенов\"\n\nГраебер-аналогия красивая, но: в долговой экономике есть механизм принуждения (суд, репутация, социальная связь). В SyncBack принуждение = только natural punishment через S-score. Если я накопил хороший I-score, мой S начинает падать → trust × 0.1. Но мои данные при этом в сети → я могу просто уйти с тем что успел забекапить. Нет механизма \"вернуть долг\".\n\nЭто нормально для честных участников. Но для рационального эгоиста: участвуй год, накопи хороший I, получи escrow tier 3, забери данные, уйди. Repeat с новой нодой.\n\n### 3.5. \"16 преимуществ RaptorQ — серьёзных недостатков: 0\"\n\nДокумент raptorq.md сам перечисляет недостатки, но dismisses их слишком быстро. Недостаток 5 (\"зрелость реализаций, ~200 stars, меньше battle-testing\") для production системы хранения данных — это не \"незначительно\". `reed-solomon-simd` имеет десятки тысяч deployments. `raptorq` crate — сколько? Данных нет. Для системы которая хранит единственную копию данных пользователя это существенный риск.\n\nНедостаток 4 (\"CPU overhead, бенчмарки нужны\") listed как открытый вопрос #1. S-score = pairwise storage ratio.\n\nНо S-score должен считаться по \"сколько я храню для identity X vs сколько они для меня\". Если устройство A хранит для peers A, C, E — они считают S отдельно для каждого device NodeId. Но владелец хочет один агрегированный S на уровне identity.\n\nВ документе написано \"S-score per device-peer pair\". Когда происходит переназначение пира между устройствами — S-score ломается (история у одного device, новые отношения с другим).\n\n### 5.4. \"Семья символов fungible\" vs \"ESI tracking для PoS\"\n\nRaptorQ: символы fungible — \"ни один не особенный\".
