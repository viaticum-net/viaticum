# Use cases и edge cases

*2026-03-11*

## 1. Коммерческие услуги поверх сети

Кто-то запускает платный сервис хранения, используя SyncBack протокол.

**Со стороны сервиса:** "очень надёжная нода". Высокий uptime, много хранит, высокий I и S. Протоколу всё равно ПОЧЕМУ нода надёжна. Сервис получает высокий trust заслуженно.

**Со стороны клиента:** фрилоадер. Платит сервису внешним способом (деньги), для сети — нода с S≈0. Данные в безопасности потому что сервис хранит их напрямую.

**Для сети:** ничего не меняет. Сервис реально хранит шарды → реально полезен. Клиент фрилоадит → trust низкий → сеть не даёт кредит, которого он не заслужил.

**Вывод:** коммерческий сервис — onramp для людей, которые хотят бекап без участия. Как VPN для Tor. Протокол не запрещает, не поощряет, просто не замечает.

## 2. NAS помогает другу

Сценарий: у друга низкий trust (диск полный, S≈0). Он не может обеспечить надёжный бекап. У меня NAS, хочу помочь ему через протокол, без прямого бекапа.

**Решение:** специальный механизм не нужен.

1. NAS присоединяется к сети, хранит для всех, получает trust
2. NAS добавляет friend's identity в allowlist (`trusted_identities` в конфиге)
3. Друг добавляет NAS как партнёра
4. Weighted placement: NAS надёжен → друг кладёт максимум шардов на NAS (до cap=6)

**Ключевое:** при 5-of-15 и 6 шардах на NAS — друг может восстановиться с одного NAS. 6 > 5 = restore возможен даже если вся остальная сеть друга потеряна.

**Whitelist означает:**
- NAS не дропает шарды друга под disk pressure
- NAS не применяет escrow при restore друга
- NAS приоритизирует хранение шардов друга

**Что нужно в реализации:** одна настройка — `trusted_identities: [friend_pub_key]`. Пара строк конфига, не протокольная фича.

Друг при этом остаётся фрилоадером для остальной сети (S≈0, trust низкий). Но ему всё равно — данные на NAS, а NAS надёжен. Сеть не страдает — NAS реально полезен.

## 3. Ransomware и удаление файлов

### Проблема

Вирус-шифровальщик шифрует/удаляет файлы. Демон видит "файлы пропали" — не отличает от "пользователь сам удалил".

### Решение: инерция + cooldown

**Демон (owner side):**
- Файл удалён локально → демон помечает "pending delete" в локальной БД
- Cooldown 4 недели: PoS challenges продолжают отправляться
- Через cooldown → отправляет signed delete message holders
- Пользователь заметил вирус → отменяет pending delete → отправляет cancel_delete → шарды спасены

**Holder side:**
- Получает delete → ставит cooldown таймер (4 недели)
- Получает cancel_delete до истечения cooldown → шард сохраняется
- Cooldown истёк → удаляет шард

**Двойной cooldown:** на стороне демона (не спешит слать delete) + на стороне holder (не спешит удалять). Два барьера между вирусом и потерей данных.

### Молчание ≠ удаление

Если owner замолчал (потеря устройства, болезнь, тюрьма) — holder НЕ удаляет шарды. Приоритет хранения определяется owner's trust:
- Высокий I-score (годы в сети) → holder хранит месяцами-годами
- Низкий I-score → holder дропает при нехватке места

### Обновление файлов (пережал фото)

Новая версия = новый file_id = новые шарды. Старые шарды остаются (никто не отправлял delete). При disaster recovery — восстанавливаются все доступные версии. Пользователю пойдут и старые фото — лучше чем ничего.

### Что не покрываем (edge case)

"Удалил старые файлы чтобы освободить место и забекапить новые" — cooldown задержит освобождение storage у holders. Редкий случай, игнорируем в v1.
