# Часть 0. Стратегические принципы

## 0.1 Центральный тезис: ценность проекта — механизм доверия

Erasure coding, шифрование, P2P-транспорт, NAT traversal — всё это решённые задачи с production-grade библиотеками. **Единственная нерешённая проблема** — как незнакомцы договариваются хранить данные друг друга без посредника.

Samsara (2003) описала claim exchange, но без временной модели и без async verification. GNUnet имеет trust accounting, но для bandwidth, не для storage. Autonomi пробовал крипто-токены — привлёк фармеров, не пользователей. **Никто не собрал работающий механизм доверия для P2P storage.**

Это — интеллектуальная core value проекта. Всё остальное — pluggable implementation details.

## 0.2 Что есть протокол, а что — реализация

**Протокол (core, ценность проекта):**
- PID-reputation с временем как неподделываемым ресурсом
- Асинхронный proof-of-storage через "почтальонов" (relay)
- Репутация почтальонов как часть единой модели доверия
- Органическое формирование кластеров через усиление стабильных связей
- Bootstrap через "залог" пространством и/или relay-сервис
- Tiered trust (inner / outer / stranger) с разной частотой верификации
- Federated network model — кластеры доверия + cross-cluster storage

**Реализация (pluggable, заменяемое):**
- Конкретный erasure coding (Reed-Solomon, fountain codes, ...)
- Конкретное шифрование (XChaCha20, AES-256, ...)
- Конкретный transport (iroh, libp2p, Syncthing BEP, ...)
- Конкретный DHT (mainline BitTorrent, Kademlia, ...)
- Конкретный content hash (BLAKE3, SHA-256, ...)

Протокол описывает **что** проверять и **когда** доверять. Реализация решает **как** шифровать и **куда** класть байты.

## 0.3 Стратегические принципы проекта

### Open Source — must have

Все три предшественника (Wuala, CrashPlan, BuddyBackup) были проприетарными и умерли вместе с компаниями. Ни строчки кода не осталось. Open source = проект переживёт автора.

Автор зарабатывает репутацию и реализацию, не деньги.

### Protocol first

Код устаревает, протокол живёт десятилетиями. BitTorrent (протокол) пережил десятки клиентов. HTTP пережил Netscape. Email пережил всех. Формат — RFC/BEP-style спецификация, которую любой может реализовать.

Идеи — главная ценность проекта. Учитывая что никто не решил эту задачу за 23 года (с Samsara 2003), работающий механизм доверия — это вклад в computer science, не просто ещё один P2P-клиент.

### Reference implementation, not THE implementation

Код автора — "вот так можно реализовать протокол." Не THE client, а A client. Кто-то напишет лучше на Go, кто-то сделает GUI, кто-то встроит в NAS. Проект **сознательно проектируется для замены собственного кода.** Это контринтуитивно, но именно это делает проект бессмертным.

### "Работает для двоих"

Система даёт ценность уже при 2 участниках (ты и друг), и становится лучше с ростом. Не "нужно 1000 нод чтобы запустить." Autonomi требовал критическую массу → не набрал → умер. BitTorrent работает даже с 2 пирами. Инкрементальная ценность, не пороговая.

### No single org to kill

Если автор завтра уйдёт из проекта — сеть продолжит работать. Нет сервера который можно выключить, нет компании которую можно закрыть, нет аккаунта который можно заблокировать. Это **политическое заявление**: никто не может признать тебя "человеком второго сорта" и отключить от твоих данных.

### Tolerate imperfection

98% reliability вместо 99.999% означает на порядок более простую систему. Предшественники пытались конкурировать с AWS по надёжности и проиграли. Мы конкурируем с "ничего" — и 98% бесконечно лучше чем 0%.

### Adversary model: ленивые, не злые. Главный враг — churn, не атакующий

Проектировать для selfishness, не для warfare. Greedy-but-rational actors (Samsara's threat model). BitTorrent не защищён от state-level adversary, но отлично работает с миллионами ленивых юзеров.

Ключевой вопрос для любой атаки: **зачем?** В системе нет финансовых активов (нет токенов), данные зашифрованы и бесполезны атакующему, конкурентов нет (аудитория — люди которые не платят за облако), таргетированная деструкция практически невозможна (шарды зашифрованы + content-addressed + распределены).

**Реальная угроза — не атаки, а естественный churn.** Люди уходят потому что надоело, купили новый компьютер, переехали, забыли. Это не атака — это жизнь. Система должна переживать churn, а не отражать осады.

Не строить крепость — **строить устойчивую деревню.** Деревня выживает не потому что защищена от армий, а потому что люди приходят и уходят, а структура остаётся.

### No gatekeepers

Никаких аккаунтов, KYC, одобрений. Скачал → запустил → участвуешь. Gatekeeper = single point of control = single point of censorship.

### Data sovereignty

Твои ключи, твои данные. Seed phrase на бумажке в сейфе = полный контроль. Никто — ни автор протокола, ни relay-оператор, ни пир — не может прочитать, заблокировать или удалить твои данные.

### Protocol defines trust, user defines policy

Протокол определяет **как считать доверие** (PID-score, async verification, relay reputation). Что с этим доверием делать — решает каждый пир самостоятельно.

Протокол говорит: "пир X имеет score {P=0.9, I=5000, D=0.0}." А дальше:
- Юзер A решает: "4-of-10 для фото, мне хватит"
- Юзер B решает: "3-of-20, я готов отдать 500 ГБ за максимальную надёжность"
- Юзер C добавляет ключи друзей как permanently trusted и хранит только у них
- Юзер D ставит 6-of-8 и доволен

Один протокол, одна сеть, **разные политики.** Как TCP/IP — протокол не знает что ты передаёшь, он просто доставляет.

Следствия:
- Нет споров о "правильных" параметрах — нет governance для решений о defaults
- Tier 1/2/3 — не свойство протокола, а конфигурация пользователя
- "SLA 99.9%" — пожалуйста, увеличь redundancy и отдай больше места
- "Доверяю только своим" — храни их ключи, верифицируй строже
- Reference implementation предлагает defaults, но каждый меняет под себя

Это исключает целый класс конфликтов в сообществе: нет "правильного" способа использовать систему, есть **твой** способ.

### No feature creep

Это backup. Не sync. Не sharing. Не social network. Не messaging. Одна задача, решённая хорошо.

## 0.4 Сознательные отказы

**Нет бизнес-модели** — и не нужна. Wuala нужна была бизнес-модель → LaCie → централизация → смерть. Если проект не требует денег на инфраструктуру (P2P не требует) — бизнес-модель это liability, не asset.

**Нет foundation/governance на старте.** Протокол описан, код открыт, кто хочет — форкает. Governance нужна когда есть что governance-ить.

**Нет крипто-токенов.** Токены привлекают фармеров и спекулянтов, а не пользователей. Autonomi это доказал. Репутация через время — лучший incentive mechanism.

# Часть I. Постановка задачи

## 1.1 Проблема

Личные данные обычного человека — документы, фото, видео — не защищены от потери. Существующие решения:

- **Облачные сервисы** (Google Drive, iCloud, Dropbox) — платные, требуют аккаунт, зависимость от компании. Завтра могут закрыть доступ, поднять цену, заблокировать аккаунт по любой причине.
- **Второй/третий диск** — требует покупки оборудования, физического хранения, дисциплины.
- **NAS / self-hosted** — высокий порог входа, стоимость, обслуживание.

Все эти решения требуют либо денег, либо экспертизы, либо доверия к третьей стороне.

## 1.2 Целевая аудитория

Обычные люди, у которых:
- Есть 200-500 ГБ свободного места на диске
- Есть 30-200 ГБ данных, которые жалко потерять
- Нет желания платить за облако или думать о серверах
- Нет 10-20 технически подкованных друзей для кооператива
- Есть готовность принять 1-2% потерь при восстановлении

## 1.3 Ключевая идея

Гибрид Syncthing и BitTorrent для бекапов:
- Зашифровать файлы
- Разложить их между участниками сети
- Хранить чужие данные и получать за это репутацию
- Никто не может пользоваться другими, не давая своего

**Тонкая прослойка над проверенными годами технологиями**, а не система с нуля.

## 1.4 Что это НЕ

- **Не аналог S3.** Нет API, нет мгновенного доступа, нет SLA.
- **Не sync.** Файлы не синхронизируются в реальном времени.
- **Не горячее хранилище.** Восстановление занимает дни-недели, не минуты.
- **Не для корпоратов.** Личные данные, личная ответственность.

## 1.5 Приоритеты данных

| Тип данных | Типичный объём | Приоритет | Характер |
|---|---|---|---|
| Документы (PDF, DOCX, таблицы, конфиги) | 1-10 ГБ | Критичный | Мелкие файлы, иногда меняются |
| Фото (JPEG, HEIC, RAW) | 20-100 ГБ | Высокий | Много файлов, иммутабельные (append-only) |
| Короткие видео (личные) | 10-50 ГБ | Средний | Append-only, крупные файлы |
| Большие видео (фильмы, сериалы) | N/A | Не бекапится | Скачиваемый контент, не личные данные |
| **Итого "реально важного"** | **30-160 ГБ** | | |

Фото — основной объём важных данных. Документы — самые критичные, но крошечные. Видео — по остаточному принципу.

# Часть II. Обзор предшественников

## 2.1 Мёртвые проекты

### Wuala (2008-2015)

**Что делал:** Пользователи отдавали X ГБ дискового пространства → получали X ГБ облачного хранения. Erasure coding (n-of-k), клиентское шифрование. Ближайшая историческая реализация описываемой идеи.

**Что пошло не так:**
- Измерения Eurecom (2012): через неделю после загрузки файлы скачивались преимущественно с центральных серверов, а не от пиров. Peer contribution оказался маргинальным — из-за нестабильности и медленного upload домашних подключений.
- Стоимость bandwidth в датацентрах упала ~10x между 2008 и 2011 годами.
- Мобильные устройства: P2P-клиент в фоне убивает батарею. К 2011 смартфоны стали доминировать, пользователи отключали фоновый upload.
- Сооснователь Luzius Meisser прямо назвал 4 причины: дешёвый bandwidth, маргинальный peer contribution, сложность гибридной архитектуры, mobile constraints.
- В 2011 LaCie перевёл на чисто централизованное хранение. В 2015 закрыт полностью.

**Урок:** P2P хранение не может конкурировать с облаком в real-time access и bandwidth. Но наша задача — не конкурировать. "Холодный бекап" не требует ни real-time, ни высокого bandwidth.

### CrashPlan P2P (†2018)

**Что делал:** Зашифрованные бекапы на компьютеры друзей. Бесплатно. P2P фича была частью потребительского продукта Code42.

**Что пошло не так:**
- Code42 убил весь потребительский продукт в августе 2017, заявив что поддержка "individuals with little to no computer knowledge" требует дорогой инфраструктуры, которая не окупается при потребительском ценообразовании.
- P2P фича не была выделена в отдельный продукт.
- Петиция на Change.org с просьбой открыть код — отказ.

**Урок:** Спрос подтверждён. Проблема — бизнес-модель, не технология. Open-source проект без необходимости окупать поддержку не имеет этой проблемы.

### BuddyBackup (†2022)

**Что делал:** UK стартап. Бекап на диски друзей, без центрального сервера. Полностью бесплатно. Концептуально очень близко к описываемой идее.

**Что пошло не так:** Проприетарный код, нет federation, умер вместе с компанией. Никакого open-source наследия.

**Урок:** Правильная идея, неправильная форма. Должен быть open-source протокол, а не продукт одной компании.

### Общий паттерн

Все три проекта доказали что **спрос реален**. Все три погибли по бизнес-причинам (не техническим). Все три были проприетарными — ни один не оставил открытого кода или протокола. Все три пытались быть "облаком" с real-time доступом, что ставило P2P в невыгодное сравнение с датацентрами.

## 2.2 Живые проекты, не решающие задачу

### Tahoe-LAFS

**Статус:** Живой, v1.20.0 (декабрь 2024), Python, волонтёрское сообщество.

**Что даёт:** Лучший существующий erasure-coded, client-side encrypted, serverless storage. Клиент загружает зашифрованные erasure-coded шарды (по умолчанию 3-of-10) на набор storage-серверов. Ключ шифрования у клиента, серверы видят только шифртекст.

**Чего не хватает:** Никакого reciprocity/fairness. Из собственной wiki (AccountingDesign ticket): "Tahoe clients choose servers purely on the basis of their nodeids and do not compute or use any notion of reliability." Нет tit-for-tat, нет кредитов, нет обмена. Можно запустить "friend grid", но софт ничего не enforce-ит.

**Мог бы быть базой?** Да, как storage/erasure-coding/encryption layer. Но missing piece — reciprocity — это ровно то, что нужно построить.

### Syncthing

**Статус:** Очень живой, Go, активно поддерживается.

**Что даёт:** Непрерывная синхронизация файлов. С 2021 — "untrusted (encrypted) device" mode: можно хранить зашифрованные данные на устройстве, оператор которого не может их прочитать.

**Чего не хватает:** Sync, не backup — удаления пропагируются. Нет erasure coding (полные копии). Нет fairness accounting. Нет версионирования (нужно layerить restic/Duplicati).

**Мог бы быть базой?** Как transport layer — возможно, но BEP (Block Exchange Protocol) тесно связан с Syncthing internals. Нет standalone библиотеки. Команда Syncthing подтвердила (форум, июль 2024): "Nothing built in" для использования как библиотеки.

### Autonomi (ex-MaidSafe / Safe Network)

**Статус:** Фактически мёртв. v1.0 запущен февраль 2025, официально закрыт 5 марта 2026. v2.0 в разработке, сроки неизвестны. Проекту MaidSafe ~20 лет.

**Что произошло с v1:**
- Токен ANT на Arbitrum (Ethereum L2). 240M токенов на эмиссию для нод.
- Крупные операторы запустили модифицированные ноды для фарма токенов.
- Январь 2026: эмиссию приостановили → массовый уход нод → repair storm на несколько дней.
- Только 2.94% бюджета эмиссии использовано за год работы.
- Токен -74% от ATH.
- Обычный юзер с нодой 35 ГБ за 3 недели заработал 0 и не смог загрузить данные без покупки токенов.

**Урок:** Крипто-токены привлекают фармеров и спекулянтов, а не реальных пользователей. Токен-стимулы создают mercenary nodes, которые уходят когда стимул кончается — вызывая correlated failure. Архитектурно интересен (libp2p, self-encryption, автоматический repair), но экономическая модель провалилась.

### GNUnet

**Статус:** Живой, GNU project, активно поддерживается.

**Что интересно:** Единственный активный проект с **reputation без крипто-токенов**. Ноды трекают сколько bandwidth и storage потребил/предоставил каждый пир, приоритизируют хороших участников. Excess-based economic model.

**Чего не хватает:** Спроектирован для анонимного файлошаринга, не для гарантированного бекапа. Персистентность данных не гарантирована.

**Полезно:** Trust accounting mechanism заслуживает изучения для заимствования идей.

### Nextcloud Backup (P2P Mode)

**Статус:** Beta с ноября 2021, доступен в production. Поддерживается.

**Что делает:** Nextcloud-инстанс может бекапить на другой Nextcloud-инстанс (например, у друга). Сжатые, зашифрованные, инкрементальные бекапы. Nextcloud сам предлагает делать это взаимно.

**Чего не хватает:** Тяжёлый (нужен целый Nextcloud-стек). Нет автоматического fairness enforcement. Нет erasure coding.

### Peergos

**Статус:** Живой, AGPL, активная разработка. Построен на IPFS/libp2p.

**Архитектура:** E2E-зашифрованные файлы с пост-квантовой криптографией. Социальная сеть + файловое хранилище.

**Не подходит:** Спроектирован для sharing с известными контактами, не для хранения у незнакомцев в reputation pool.

## 2.3 Академическая база

### Samsara (Cox & Noble, University of Michigan, SOSP 2003)

**"Honor Among Thieves in Peer-to-Peer Storage"** — наиболее полная академическая работа по fairness в P2P storage без доверенных третьих сторон.

Подробный обзор: [reviews/samsara-2003-review.md](reviews/samsara-2003-review.md)

Ключевые идеи:
- **Storage claims** — несжимаемые плейсхолдеры. Хранишь чужие данные → "claim" равного размера занимает место у партнёра. Производит симметрию.
- **Probabilistic discard** — не бинарное наказание, а постепенная потеря реплик при пропуске проверок. Честные, но временно offline ноды теряют мало; мошенники — всё.
- **Claim forwarding + dependency cycles** — оптимизация overhead, но создаёт хрупкие цепочки.

Никто не реализовал Samsara в production за 23 года.

### pStore (MIT/Cornell, 2001)

"A Secure Peer-to-Peer Backup System." Chord DHT, erasure coding, client-side encryption. 30-node эксперимент: 95% файлов восстановлены при 7 из 30 узлов упавших. Без fairness — предполагает кооперативных участников.

### Lillibridge et al. (HP Labs, 2003)

"A Cooperative Internet Backup Scheme." Анализ bandwidth и storage costs. Ключевой вывод: erasure coding **радикально эффективнее** простой репликации для достижения той же надёжности.

### INRIA Survey (2007)

"A Survey of Cooperative Backup Mechanisms." Три столпа: data fragmentation/dissemination, redundancy (replication vs. erasure coding), repair mechanisms. Free rider problem — центральная нерешённая проблема.

### Churn measurements

- **Stutzbach & Rejaie (IMC 2006):** Замеры Gnutella. Медианная сессия ~1 час. Heavy-tail distribution: большинство сессий короткие, но немногие — очень длинные.
- **Bhagwan, Savage, Voelker (IPTPS 2003):** Замеры Overnet DHT. Availability сильно бимодальная. Значительная доля нод появляется ненадолго и только раз.
- **Steiner et al. (IEEE/ACM ToN, 2009):** KAD DHT, многомесячные замеры. Peer, стабильный на протяжении недели, может уйти через месяц.

### Data durability under churn

- **INRIA RR-6392 (2007):** Аналитические модели. Data lifetime при простой репликации катастрофически падает даже при умеренном churn, если repair медленный. Repair rate должен превышать failure rate, иначе система деградирует к нулю.
- **Toka et al. (Eurecom):** Системы должны динамически регулировать redundancy на основе наблюдаемого churn. Даже с динамической адаптацией, "estimate lag" может вызвать каскады потерь.

# Часть III. Минные поля

Систематический анализ причин провала P2P backup систем.

## 3.1 Tit-for-tat не работает для хранения

**BitTorrent tit-for-tat работает** потому что три условия выполнены одновременно:
1. Каждый пир имеет копию контента, который все хотят — обмен симметричен
2. Обмен происходит в настоящем времени — upload сейчас, download сейчас
3. Дефекция немедленно обнаруживается и немедленно наказывается (choking)

**Хранение нарушает все три условия:**
1. Асимметрия обязательств: хранение — долгосрочный commitment (месяцы, годы) без немедленной взаимной выгоды.
2. Временное разделение: долг не может быть enforce-ен в момент, когда он нужен. Партнёр дефектирует через 18 месяцев — наказывать некого.
3. Асимметрия потребности: данные нужны только при катастрофе. "Наказание" (потеря данных) совпадает с моментом, когда ты в наихудшем положении.

**Следствие для проекта:** Не пытаться строить "справедливость" — строить **устойчивость к несправедливости**. Избыточность + lazy repair + proof-of-storage вместо наказания за дефекцию.

## 3.2 Churn убивает данные быстрее, чем кажется

Академические модели INRIA показывают: при реалистичных churn rates и repair lag в часах, данные быстро умирают. Для домашних peer-сетей (ноутбуки закрываются, пользователи переезжают, ISP падает) repair pipeline всегда полон.

Фундаментальное противоречие: для безопасности нужна либо высокая избыточность (5-10x), либо быстрый repair. Высокая избыточность множит storage cost. Быстрый repair требует bandwidth, которого у домашних пользователей нет. Два требования в противоречии.

**Наш ответ:** Постоянная времени = неделя. Это радикально меняет математику. См. раздел 4.3.

## 3.3 Repair storm

Когда много пиров уходят одновременно (correlated failure — обновление ОС, отключение электричества, смена экономических стимулов), оставшиеся пиры пытаются repair одновременно → перегрузка → каскадные потери.

**Реальный пример:** Autonomi, январь 2026. Приостановка токен-эмиссии → массовый уход farming-нод → repair storm на "several days" (задокументировано в developer update January 22, 2026).

**Наш ответ:** Lazy repair. 160 ГБ за 7 дней = 260 КБ/с. Repair storm при постоянной времени в неделю — не storm, а лёгкий ветер.

## 3.4 Холодный старт

Chicken-and-egg: мало пиров → низкая надёжность → никто не хранит важное → нет роста. Все deployed решения либо субсидировали центральные серверы, либо платили токенами (привлекая mercenary nodes), либо ограничивали доступ (invite-only).

**Наш ответ:** "Залог" дисковым пространством (раздел 4.5). Новичок сразу выделяет место и начинает хранить чужое → instant score → может бекапить своё. Порог входа = "выдели папку, подожди час."

## 3.5 Асимметрия upload

Домашний интернет: download 200+ Mbps, upload 10-50 Mbps. Кабельные планы с 500/20 или 100/10 — типичны. Fiber (симметричный) — далеко не у всех.

Initial backup 200 ГБ при 10 Mbps upload = 44 часа. При этом нужно ещё хранить чужие данные и отдавать по запросу.

**Наш ответ:** Постоянная времени = неделя. Initial backup за неделю при 10 Mbps = можно загрузить ~750 ГБ. Реальные 100-160 ГБ — за 2-3 дня. Инкремент потом — несколько фото в день, мегабайты.

## 3.6 NAT traversal — 30% пиров недоступны напрямую

Замеры libp2p (4.4M попыток, 167 стран): UDP/TCP hole punching работает в **70% ±7.1% случаев**. Symmetric NAT (enterprise, mobile carriers), CGNAT (Восточная Европа, ЮА, Ближний Восток) — hole punching не работает.

Стандартный Circuit Relay v2 в libp2p: ограничение 128 KB и 2 минуты — непригодно для гигабайтов.

**Наш ответ:** "Попробуй завтра." При постоянной времени в неделю — десятки попыток. Вероятность что за неделю ни разу не достучался до живого пира ≈ 0. Для relay: собственные relay-ноды или использование iroh (relay без ограничений по объёму, rate-limited).

## 3.7 Adversarial storage — как проверить что пир реально хранит данные

Базовая атака: пир соглашается хранить 10 ГБ. Хранит месяц. Удаляет чтобы освободить место. Продолжает отвечать на "are you online?" pings. При попытке restore — данных нет.

**Cryptographic solutions:**
- **Provable Data Possession (PDP)** — compact proof что сервер хранит конкретные блоки. ~150ms verification, ~2.34 KB communication overhead.
- **Proof of Retrievability (PoR)** — PDP + error-correcting codes. Доказывает не только possession, но и recoverability.
- **Filecoin Proof of Spacetime** — too heavy (GPU, часы на sealing). Для домашних пользователей непригодно.

**Наш ответ:** Merkle-tree challenges. Простой challenge-response:
1. При upload: строим Merkle tree из блоков шарда, сохраняем root.
2. Challenge: "отдай leaf в позиции N и Merkle proof."
3. Verifier проверяет proof против известного root.
4. Раз в неделю, lightweight. Не ответил дважды подряд — начинаем миграцию.

## 3.8 Legal/liability

Если хранишь зашифрованные шарды для незнакомцев — что юридически?

- Freenet/Tor: plausible deniability — не знаешь что хранишь (не можешь расшифровать).
- US 8th Circuit (2020): в одном деле суд не смог отличить active requester от passive relay node и исключил evidence.
- EFF Legal FAQ для Tor exit operators: "legal but has resulted in searches and investigations."

**Для нашей системы:**
- Шарды зашифрованы до erasure coding — пир не может прочитать содержимое.
- Erasure-coded шард без других шардов бесполезен — даже с ключом не восстановить файл.
- Двойная защита: шифрование + fragmentation.
- В federated модели (кластеры знакомых + межкластерный обмен) риск ниже чем в полностью анонимной сети.

## 3.9 Почему BitTorrent выжил 20 лет (и что из этого трансплантируемо)

**Дизайн-решения, давшие устойчивость:**

1. **Нет persistence state.** Swarm работает даже если все ноды были offline вчера. Нет long-term obligation.
2. **Контент self-verifying.** SHA-1 хэши каждого куска. Нельзя дать плохие данные. Доверяешь математике, не пирам.
3. **Нет single point of failure.** Trackers закрыли → DHT работает. Magnets заменили torrent-файлы.
4. **Partial availability useful.** 50% кусков = 50% файла. Graceful degradation.

**Что можно заимствовать:**
- Content-addressed, hash-verified chunks (как в Tahoe-LAFS, Storj)
- Нет доверия к individual nodes — erasure coding
- DHT для routing без центральной зависимости
- Optimistic unchoking / randomized partner selection

**Что НЕ трансплантируемо:**
- Tit-for-tat для хранения (работает для bandwidth, не для storage commitments)
- Graceful degradation on popularity (бекап требует durability, не popularity-proportional availability)
- Индифферентность к data loss (торрент умер — ОК; бекап умер — катастрофа)

# Часть IV. Проектные решения

## 4.1 Ключевой принцип: "Холодный бекап"

Ближайшая аналогия — коробка с фотографиями у родителей в другом городе:
- Положил и забыл
- Не проверяешь каждый час
- Если нужно — едешь на выходных
- Если 2-3 фото потерялись — ну ок

**Ни один из убитых проектов так не думал.** Wuala, CrashPlan, BuddyBackup — все пытались быть "облаком", real-time sync, мгновенный доступ. И столкнулись с тем что P2P не может дать датацентровый SLA.

**Мы не пытаемся. И поэтому задача на порядок проще.**

### Сравнение параметров

| Параметр | "Как облако" (предшественники) | "Холодный бекап" (наш подход) |
|---|---|---|
| Repair start | Через 1 час | Через 7 дней |
| Repair speed | Максимальный | ~260 КБ/с фоном |
| Peer online requirement | >90% | >10% (3ч/день хватит) |
| Verification | Каждые 10 мин | Раз в неделю |
| Recovery time | Минуты | Дни-недели |
| Нужен relay 24/7 | Да | Нет, retry later |
| Пир = ноутбук | Непригодно | Отлично работает |

### Что это разблокирует

**Churn перестаёт быть проблемой.** Пир offline 3 дня — не churn, а ноутбук закрыт. Подождём неделю. Академические модели INRIA считали repair lag в часах и получали страшные цифры. При repair lag = 7 дней + достаточная избыточность — математика совершенно другая.

**Repair storm исчезает.** 10 пиров ушли одновременно? Растяни repair на неделю. 160 ГБ за 7 дней = 260 КБ/с upload. Ничто для любого домашнего интернета.

**Availability requirement падает радикально.** Пир online 4 часа в день (ноутбук) — отличный участник. За неделю — ~28 часов online. Этого хватит для десятков ГБ.

**NAT traversal failures — просто попробуй завтра.** Не смог подключиться? Попробуем через 6 часов. За неделю — десятки попыток.

**Верификация — раз в неделю.** Proof-of-storage challenge раз в 7 дней. Bandwidth cost = копейки.

## 4.2 Федеративная сетевая модель

### Почему не "кооператив друзей" и не "полностью открытая сеть"

**Кооператив друзей (10-20 знакомых):** Технически проще, но у большинства людей нет 10-20 технически подкованных друзей для такого. "Найди 15 друзей" — не продукт, а DIY.

**Полностью открытая сеть (все незнакомцы):** Максимальная сложность: Sybil attacks, free-riding, trust bootstrap, global consensus. Все предшественники пытались решить это и провалились.

**Наш выбор: федерация.** Система сама разваливается на слабо связанные кластеры. Внутри кластера — высокое доверие. Между кластерами — умеренное. Чужаки — низкое, но с путём к повышению.

### Архитектура сети

```
┌─────────────────────────────────────────────┐
│            Open Network (DHT)               │
│                                             │
│  ┌──────────┐         ┌──────────┐         │
│  │ Cluster A │◄───────►│ Cluster B │         │
│  │ 8 peers   │         │ 12 peers  │         │
│  │ high trust│         │ high trust│         │
│  └──────────┘         └──────────┘         │
│       ▲                      ▲              │
│       │                      │              │
│       ▼                      ▼              │
│   [solo nodes, newcomers, drifters]         │
│   low trust, heavy verification             │
└─────────────────────────────────────────────┘
```

### Три уровня доверия

| Уровень | Кто | Верификация | Redundancy |
|---|---|---|---|
| **Inner** | Стабильные пиры в кластере, месяцы совместного хранения | Раз в неделю | 4-of-10 |
| **Outer** | Пиры из других кластеров, средняя история | Раз в день | 3-of-10 |
| **Stranger** | Новички, ненадёжные | Каждые 4 часа | 3-of-15 |

### Органическое формирование кластеров

Кластеры не назначаются. Они формируются **естественно** по принципу усиления стабильных связей:

1. Новый юзер приходит → система даёт несколько случайных пиров (optimistic unchoking, как BitTorrent)
2. Он хранит их шарды, они хранят его
3. Через неделю: пир X online 95% времени, пир Y — 20%. Система переносит шарды от Y к более надёжному Z
4. Через месяц: 8-12 пиров с взаимно стабильным обменом. Это кластер. Не потому что "друзья", а потому что **доказали друг другу надёжность**

BitTorrent делает ровно то же при выборе пиров для unchoke — только timescale не секунды, а недели.

### Федерация между кластерами

Зачем: **geographic & failure diversity.** Если все пиры в одном городе — отключение электричества убивает всех.

Механизм:
- Каждый кластер хранит **10-20% шардов в других кластерах**
- Кластеры связаны через "bridge nodes" — пиры, состоящие в двух кластерах
- Cross-cluster шарды имеют более агрессивный erasure coding

## 4.3 Tiered data model

### Erasure coding по приоритетам

```
Tier 1: Документы     → 5-of-15 (выдерживает 10 потерь)  → ~3x overhead
Tier 2: Фото          → 4-of-10 (выдерживает 6 потерь)   → ~2.5x overhead
Tier 3: Короткие видео → 6-of-10 (выдерживает 4 потери)  → ~1.7x overhead
```

### Пример: юзер с 100 ГБ данных

| Tier | Данные | Overhead | На сети | На каждого пира (15 пиров) |
|---|---|---|---|---|
| 1 (документы) | 5 ГБ | 3x | 15 ГБ | 1 ГБ |
| 2 (фото) | 60 ГБ | 2.5x | 150 ГБ | 10 ГБ |
| 3 (видео) | 35 ГБ | 1.7x | 60 ГБ | 4 ГБ |
| **Итого** | **100 ГБ** | | **225 ГБ** | **15 ГБ** |

Каждый пир отдаёт 15 ГБ из своих свободных 200-500 ГБ. Абсолютно реально.

### Свойства фото как идеального формата для P2P backup

- **Иммутабельные:** JPEG/HEIC не меняются после создания
- **Content-addressed хранение:** записал раз, хэш не меняется
- **Инкрементальный бекап:** = "добавь новые фото" без пересчёта старого
- **Потеря 1-2%** фото за 5 лет — ожидаемый и приемлемый результат
- **Основной объём** (60-80% важных данных типичного юзера)

### Документы — специальная обработка

- Мелкие файлы, иногда меняются
- Нужно версионирование (append-log или snapshots)
- Маленький объём → можно позволить максимальную избыточность
- Критичность максимальная → tier 1 с redundancy 5-of-15

## 4.4 Репутация как PID-контроллер

### Ключевой инсайт: время неподделываемо

Bandwidth можно купить. Storage можно купить. Uptime можно симулировать ботфермой. **Время подделать нельзя.**

Пир с историей 2 года × 10 ГБ хранения — это 2 реальных года жизни. Атакующий не может ускорить время. Это лучший anti-Sybil механизм без блокчейна.

### PID-модель репутации

По аналогии с PID-контроллером из теории управления:

**P (Proportional) — что прямо сейчас:**
- Хранит ли шарды?
- Отвечает ли на challenges?
- Текущий storage balance

**I (Integral) — накопленная история:**
- Сколько байт × дней хранил суммарно
- Накопленная величина, которую невозможно ускорить
- 10 ГБ × 730 дней = 7300 ГБ·дней — это стоимость в реальном времени

**D (Derivative) — тренд:**
- Скорость изменения надёжности
- Early warning system: заметить что пир "умирает" **до** фактической потери данных
- Позволяет превентивный repair

### Формализация

```
trust(peer) = f(P, I, D)

где:
  P = current_stored / expected_stored           # сейчас ОК?
  I = Σ(stored_bytes × days_held) за всё время   # накопленная история
  D = trend(availability, window=30 days)         # куда движется
```

### Примеры оценки

**Новичок, 100% uptime, 1 месяц:**
```
P = 1.0  (всё хранит, всё отлично)
I = 30   (ГБ·дней — мало)
D = 0.0  (стабилен, но выборка слишком короткая)
→ trust = LOW. Под наблюдением. Мало шардов доверено.
  Это может быть Sybil-нода, или человек который уйдёт через неделю.
```

**Ветеран, online раз в 2 недели, 2 года:**
```
P = 0.5  (сейчас offline, но данные на его диске)
I = 7300 (ГБ·дней — огромная)
D = 0.0  (стабильный паттерн годами)
→ trust = HIGH. Ему можно доверить tier 1 шарды.
  Паттерн "раз в 2 недели" — идеален для системы с постоянной времени = неделя.
```

**Бывший ветеран, начал пропадать:**
```
P = 0.3  (часто offline)
I = 5000 (была хорошая история)
D = -0.4 (тренд резко вниз за последний месяц)
→ trust = MEDIUM но FALLING.
  Начинаем превентивную миграцию шардов ПОКА ЕЩЁ МОЖНО скачать.
```

**Возвращающийся пир:**
```
P = 1.0  (снова online, данные на месте)
I = 3000 (была пауза, но история не обнулилась)
D = +0.3 (был offline 2 месяца, теперь стабильно online 3 недели)
→ trust = MEDIUM и GROWING. Постепенно возвращаем шарды.
```

### D-компонент как early warning system

Самое ценное в PID-модели — derivative. Не ждать пока пир умрёт, а **заметить что он умирает:**

- Был online 20 дней из 30, стал 10 из 30 → D отрицательный → превентивная репликация его шардов к другим, **пока он ещё жив и можно скачать**
- Был раз в 2 недели, стал раз в неделю → D положительный → можно доверить больше

При постоянной времени = неделя D считается за скользящее окно 30-90 дней. Изменения ловятся за недели до реальной потери. Это **принципиально лучше** чем бинарный подход "online/offline."

### Anti-Sybil через время

| Атака | Защита |
|---|---|
| Sybil (100 фейковых нод) | У каждой I ≈ 0. Никто не доверит данные месяцами |
| "Накопил trust, удалил всё" | D резко отрицательный → instant repair. Ущерб ограничен одним пиром |
| Долгосрочный Sybil (2 года) | 100 нод × 2 года × 10 ГБ = 2 ТБ реального хранения. Атака дороже ущерба |
| Постепенный уход | D ловит тренд за недели. Система мигрирует данные заранее |

Элегантное свойство: если атакующий 2 года честно хранит 10 ГБ чтобы набрать trust — он потратил **больше ресурсов, чем стоят данные которые он мог бы уничтожить.** Атака стоит дороже ущерба = нерентабельна.

### Локальность вычислений

Каждый пир считает reputation **сам**, про **своих** партнёров. Нет глобального consensus. Нет голосований. Нет блокчейна. Ты сам решаешь кому доверяешь — как в жизни.

```
# Каждый пир ведёт локальный лог:
# [(timestamp, peer_id, was_online, bytes_verified), ...]

# Раз в неделю:
score_current = responded_to_challenge ? 1.0 : 0.0
score_history = total_gb_days / max(days_known, 30)
score_trend = avg_availability(last_30d) - avg_availability(prev_30d)

# Решения:
if score_trend < -0.3:  начать превентивный repair
if score_history < 100:  не доверять tier 1 шарды
if score_current == 0 and days_offline > 14:  repair
```

## 4.5 Bootstrap: вход в сеть

### Проблема

Новичок приходит с score = 0. Никто не хочет хранить его данные. Как разорвать замкнутый круг?

### Решение: "Залог" дисковым пространством (Samsara's claim exchange, упрощённый)

1. Новичок при входе выделяет, скажем, 100 ГБ
2. Система сразу заполняет их чужими шардами
3. Он ещё ничего не бекапил, но уже хранит для других → instant score
4. Начинает бекапить своё, score постепенно балансируется

**Порог входа:** "скачай приложение, выдели папку, подожди час пока заполнится, начинай бекапить."

### Почему это работает

- Новичок немедленно полезен сети (хранит чужие шарды)
- Его вклад верифицируем с первого дня
- Если он уйдёт завтра — его шарды (чужие данные) re-replicate-ятся, ущерб минимален
- Если он останется — через неделю у него достаточный score для tier 3, через месяц — tier 2

### "Страховая" модель: upload сразу, restore — после доказательства ценности

Ключевой механизм для новичков: можешь загрузить свои данные с первого дня. Можешь верифицировать что они хранятся (proof-of-storage работает сразу). Но **забрать данные (restore) можешь только после накопления достаточного I-компонента reputation** — то есть после недель/месяцев хранения чужих данных.

**Это страховка, не заложничество.** Платишь "взносы" (хранишь для других) → получаешь право на "выплату" (restore). ОСАГО, медстраховка, пенсия — всё работает так.

**Почему это работает:**
- У сети нулевой риск. Новичок ушёл через день → garbage collect его шардов, пространство свободно.
- У новичка максимальная мотивация остаться: его данные уже там, он видит что они целы, он хочет получить доступ к restore.
- Данные **защищены с первого дня** — просто retrieve заблокирован до накопления trust.
- Edge case "загрузил вчера, сегодня диск умер": вчера бекапа не было вообще — ситуация не ухудшилась.

**Социальное доказательство:** Приватные BitTorrent-трекеры используют ratio enforcement (ratio > 1.0 чтобы качать) десятилетиями. Люди принимают это как справедливое, годами поддерживают ratio. Та же модель, storage вместо bandwidth.

**Уровни unlock (перевернутая пирамида — instant value first):**

```
День 1:     upload всего + verify + restore документов (5 ГБ — ничтожная цена для сети)
Неделя 2:   restore 10% фото (самые недавние / помеченные как важные)
Месяц 1:    restore 50% фото
Месяц 3:    restore 100% фото
Месяц 6+:   restore видео + приоритетный repair
```

Логика: документы крошечные (1-10 ГБ) — отдать их новичку стоит сети **ничего**, зато даёт **мгновенную ценность.** "Подключился вчера, диск умер сегодня, документы в безопасности" — это killer adoption moment. Сеть при этом в плюсе: новичок уже хранит 100+ ГБ чужих шардов ("залог").

Progressive unlock фото — мотивация оставаться: "вы можете восстановить 10% фото, храните ещё 2 недели для 50%." Gamification через реальную ценность, не баллы.

Конкретные пороги — user policy (принцип "protocol defines trust, user defines policy"), reference implementation предлагает defaults.

### Rate limiting

Нельзя бесконечно бекапить, отдав мало места:
- Базовое правило: `можешь_бекапить ≤ хранишь_для_других × коэффициент`
- Коэффициент зависит от trust level (для новичков ~0.5, для ветеранов ~1.5)
- Dashboard показывает баланс: "Вы храните 80 ГБ для других, можете бекапить до 120 ГБ"

## 4.6 Metadata — единственная "горячая" часть

### Проблема

Сами шарды — холодные, лежат, никому не мешают. Но **карта шардов** ("файл X разбит на шарды S1...S10, они лежат у пиров P1...P10") — критичная информация. Потерял карту = потерял всё, даже если шарды живы.

### Решение: encrypted metadata everywhere

Ключевой инсайт: **metadata зашифрована ключом владельца.** Это означает:

- Metadata — opaque encrypted blob для всех кроме владельца
- Хранить можно **у всех** без privacy-риска
- Крошечный размер (килобайты) → overhead нулевой → реплицируй агрессивно
- Атакующий не может узнать shard placement (не видит где чьи шарды)

**Правило: каждый пир, хранящий хотя бы один шард, хранит и encrypted metadata владельца этого шарда.** Пока жив хоть один шард — жив и metadata.

Уровни хранения metadata:

1. **Локальная копия** — primary, на диске юзера
2. **Encrypted replica у каждого shard-holding пира** — автоматически, как часть протокола хранения шарда
3. **Подписанная запись в DHT** — BEP44 мутабельная запись; пиры republish-ат по public key владельца (знают ключ, но не содержимое)
4. **Offline backup** — seed phrase + 2-3 anchor peer IDs

### Disaster recovery

Юзер потерял компьютер:
1. Берёт новый
2. Вводит seed phrase → восстанавливает ключи + anchor peer IDs
3. Связывается с anchor peer → получает encrypted metadata → расшифровывает
4. Если anchor peers недоступны → DHT lookup по своему public key → находит любого shard-holding пира → у того есть metadata
5. Начинает скачивать шарды
6. Медленно, неделями — но данные возвращаются

**Seed phrase содержит:**
- Master key (для derivation ключей шифрования)
- 2-3 anchor peer IDs (последние известные надёжные партнёры, I > порога)

Anchor peers обновляются автоматически при каждом backup cycle — всегда актуальный snapshot самых надёжных партнёров.

### Свойства encrypted metadata

| Свойство | Следствие |
|---|---|
| Зашифрована | Хранить у всех безопасно |
| Крошечная | Overhead нулевой, реплицируй везде |
| Shard placement скрыт | Targeted attacks существенно сложнее |
| Пиры republish DHT | Запись живёт пока живы пиры, не зависит от owner's uptime |
| Anchor peers в seed | Bootstrap без DHT возможен |

## 4.7 Асинхронная верификация: "почтальоны" и доверие к ним

### Проблема: ноды не пересекаются во времени

Нода A online в понедельник 10:00-14:00. Нода B (хранит шарды A) online в среду 20:00-23:00. Они **никогда** не пересекаются. A не может напрямую проверить B.

Наивное решение — доверить проверку ноде C, которая пересекается с обоими. Но если C и B в сговоре — C может врать что "B хранит данные."

### Решение: relay как "почтальон", а не "судья"

Verification — полностью **асинхронный** cryptographic challenge-response. Relay-нода — просто почтальон, она не может подделать результат.

**Протокол:**

```
1. A (online пн) создаёт challenge:
   {challenge_id, nonce: random, block_index: 7392, signed_by: A}
   → кладёт в gossip / DHT / любой доступной ноде

2. B (online ср) подбирает challenge:
   → читает блок #7392 с диска
   → формирует ответ: {block_data[7392], merkle_proof, signed_by: B}
   → кладёт обратно в gossip

3. A (online следующий пн) подбирает ответ:
   → проверяет подпись B (ответ действительно от B)
   → проверяет merkle_proof против сохранённого root
   → проверяет что block_data соответствует proof
   → ВЕРИФИЦИРОВАНО. Без доверия к relay-ноде C.
```

### Почему relay не может обмануть

| Атака | Почему не работает |
|---|---|
| C подделывает ответ за B | Ответ подписан private key B. C не знает ключ |
| C и B в сговоре, B удалил данные | B не может создать валидный ответ без реальных данных. Block index случайный, nonce случайный — pre-computation невозможна |
| C дропает challenge (не доставляет) | A не получает ответ → считает challenge проваленным. Mitigated: отправка через нескольких relay одновременно |
| B хранит только Merkle tree, удалил данные | Challenge требует **block_data**, не только proof. Без данных — ответ невозможен |

### Что A должна хранить для верификации

Для каждого шарда — только **Merkle root** (32 байта). Это часть metadata, реплицируется везде.

При получении block_data + merkle_proof:
1. Хэшируем block_data → получаем leaf hash
2. Проверяем merkle_proof: leaf → root
3. Root совпадает с сохранённым → шард цел

32 байта на шард × 100 шардов = **3.2 КБ** total verification data.

### Bandwidth cost

Один challenge-response = один блок (256 КБ) + Merkle proof (~1 КБ) + подписи (~128 Б).

Раз в неделю, 10 шардов = **~2.5 МБ/неделю**. Ничтожно даже через relay.

### Репутация "почтальонов" — та же PID-модель

Единственная реальная атака relay-ноды — **drop messages** (не доставить challenge или response). Это не фальсификация, а denial of service.

Решение: на relay-ноды распространяется **та же PID-репутация:**

```
relay_score(peer) = {
  P: delivered_last_week / total_relayed_last_week,
  I: Σ(messages_delivered × days) за всё время,
  D: trend(delivery_rate, window=30 days)
}
```

- Через C прошло 50 challenge-response за полгода, все доставлены → I высокий, надёжный почтальон
- Через D прошло 10, 3 потерялись → score падает, перестаём использовать

Не нужна отдельная система — **те же PID-компоненты**, просто метрика другая: "доставляет ли сообщения" вместо "хранит ли данные."

### Unified trust score

Storage reputation и relay reputation могут быть объединены в общий trust score:

```
total_trust = w_storage × storage_score + w_relay × relay_score

# Нода которая и хранит надёжно, и relay-ит честно = ценный участник сети
```

### Relay как быстрый путь для новичков

Важное следствие: relay-репутацию можно набрать **значительно быстрее** чем storage-репутацию:

- Storage: нужны недели-месяцы хранения чтобы I-компонент стал значимым
- Relay: сообщения проходят часто, feedback loop — дни

Это ещё один путь для bootstrap:
1. Новичок начинает как **relay node** (не требует storage, только bandwidth)
2. За неделю набирает relay reputation
3. Параллельно получает storage shards от сети
4. Через 2-3 недели — достаточный общий trust для размещения своих бекапов

Три пути входа в сеть:
- **Залог storage** (быстро, требует дисковое пространство)
- **Relay service** (быстро, требует только bandwidth и uptime)
- **Оба** (самый быстрый путь к высокому trust)

### Совместимость с "постоянной времени = неделя"

Асинхронный challenge-response идеально ложится на недельный цикл:

- Challenge в понедельник → ответ в среду → верификация в следующий понедельник
- Неделя прошла — всё проверено
- Никакой спешки, никаких требований к одновременному online

## 4.8 Экономика системы: долг, а не деньги

### Что является "валютой"

Не абстрактные баллы и не токены. "Валюта" — **конкретные байты на конкретном диске.** Я храню 50 ГБ для тебя, ты хранишь 50 ГБ для меня. Физические байты, верифицируемые proof-of-storage. Подделать нельзя.

Reputation (PID-score) — это **не валюта, а кредитный лимит.** Как кредитная история в банке: она определяет сколько тебе одолжат, но сама не является деньгами.

```
"Валюта" = реальные ГБ × реальные дни хранения
Reputation = лимит: сколько можешь "занять" у сети
```

### Модель долга (по Грейберу)

Дэвид Грейбер ("Долг: первые 5000 лет истории") показал что кредит/долг существовал за тысячи лет до денег. Деревня работала без монет — на обязательствах. "Я дал тебе зерно, ты мне должен." В голове каждого жителя — точная карта: кто кому должен, кто отдаст, кто нет, кого можно списать.

Наша система — формализация этого механизма для интернета.

И ключевая деталь: **деревня состоит не из отдельных людей, а из семей.** Внутри семьи — другие отношения: нет долга, нет учёта, общий котёл. Семья Петровичей — это одна единица в деревенской экономике, а внутри — безусловное доверие. Точно так же personal cluster (ноутбук + NAS + desktop + жена) — одна identity в сети, а внутри — unencrypted metadata, мгновенный restore, общий reputation.

Долг и учёт — между семьями. Не между мужем и женой.

| Деревня | Viaticum |
|---|---|
| Семья Петровичей (5 человек, один двор) | Personal cluster (laptop + NAS + desktop + partner) |
| Внутри семьи: общий котёл, нет учёта | Внутри cluster: unencrypted metadata, нет verification |
| Между семьями: "дал зерно — должны" | Между identities: "храню шарды — должны хранение" |
| "Петрович всегда отдаёт" | I = 7300 ГБ·дней |
| "Последний год хуже и хуже" | D = -0.4 |
| "Фёдор уехал, списываем" | 14 дней offline → repair → write-off |
| Каждый ведёт счёт в своей голове | Каждый пир считает reputation локально |
| Деньги не нужны, хватает памяти | Токены не нужны, хватает лога |
| Большая семья = больше рабочих рук = больше кредит | Больше devices = больше storage contribution = больше reputation |

Ключевой принцип Грейбера: **не деньги породили долг — долг породил деньги.** Токены (крипто) — это попытка ввести "деньги" в систему где достаточно "долга." Именно поэтому Autonomi привлёк фармеров, а не пользователей — деньги привлекают спекулянтов, а долг/обязательство привлекает участников.

### Write-off как естественный механизм

В деревне долги списываются. Человек умер, уехал, обеднел — долг со временем забывается. Без write-off система засоряется вечными обязательствами.

В Viaticum: пир ушёл → через 2 недели repair → через месяц его "долг" перераспределён → write-off завершён. Никакого наказания. Жизнь.

### Циклы дачи и получения

Здоровый пользовательский цикл:

```
Год 0: Пустой диск → много свободного места → "кредитор" (хранит для других)
Год 1: Диск заполняется → баланс сдвигается → "должник" (берёт больше чем даёт)
Год 2: Купил новый диск → снова "кредитор"
```

Это не эксплуатация — **это нормальная жизнь кредитной системы.** У Грейбера: фермер после урожая — кредитор, перед урожаем — должник. Деревня живёт такими циклами тысячелетиями.

### Bounded exposure: ограничение кредита

```
можешь_бекапить ≤ хранишь_для_других × коэффициент(trust_level)

Новичок:          коэфф = 0.3  (храни 300 ГБ → бекапь до 100 ГБ)
3 месяца:         коэфф = 0.7
Год+:             коэфф = 1.5  (хранишь 200 → бекапишь 300, "кредит доверия")
```

Максимальный "невозвратный долг" = реальный вклад пира × коэффициент. Как в деревне: максимум что потеряешь на должнике — столько сколько ты решил ему одолжить.

## 4.9 Threat model: реалистичная оценка угроз

### Кому и зачем атаковать?

| Мотив | Реалистичность | Почему |
|---|---|---|
| Финансовый | **Нулевая** | Нет токенов, нет денег, данные зашифрованы и бесполезны |
| Конкурентный | **Нулевая** | Аудитория — люди не платящие за облако. Нечего отнимать |
| Политический | **Минимальная** | Правительству проще конфисковать физические устройства |
| Таргетированный | **Очень низкая** | Нужно знать какие шарды чьи (зашифрованы), контролировать >70% пиров жертвы |
| "Просто так" / троллинг | **Единственная реальная** | Но стоимость входа: реальное хранение × реальное время |

### Главный "враг": не атакующий, а churn

Люди уходят потому что:
- Надоело
- Купили новый компьютер и забыли поставить клиент
- Переехали, сменили ISP
- Просто забили

Это не атака — это жизнь. И именно к этому система должна быть устойчива в первую очередь. Все механизмы (lazy repair, D-компонент, erasure coding) работают на это.

### Sybil at scale: 1000 нод по скрипту

**Сценарий "бесплатный бекап":**
- 1000 нод, каждая хранит 10 ГБ реальных данных 6 месяцев
- Стоимость: 10 ТБ × 6 месяцев + bandwidth + 1000 IP-адресов
- Выгода: 10 ТБ × 0.7 = 7 ТБ бекапа
- **Невыгодно.** USB-диск на 10 ТБ стоит $150.

**Сценарий "деструкция" (убить все ноды разом):**
- 1000 нод из 10,000 в сети = 10%
- Файл: 10 шардов (4-of-10 erasure coding) на 10 разных пирах
- Данные теряются только если ≥7 из 10 пиров — атакующий
- P(≥7 из 10 = атакующий при 10% сети) ≈ 0.00003
- На 10,000 юзеров: ~0 потерянных файлов

**Для реального ущерба нужно >50% сети**, что при 10,000 участников означает 5,000+ нод с реальным хранением на протяжении месяцев.

### Базовая гигиена (не центральная архитектура, а defaults)

```
Shard distribution policy:
- Не больше 1 шарда одного файла на пиры из одной /24 подсети
- Не больше 2 шардов одного файла на пиры из одного ASN
- Не больше 1 шарда на пиры, присоединившиеся в один день

Rate limiting:
- Не больше N новых нод с одного /24 в неделю
- Начальный storage quota растёт медленно (1 ГБ/день первый месяц)
```

Это **гигиена, не крепость.** Как замок на двери — защищает от случайного вора, не от армии. И этого достаточно, потому что армии незачем сюда приходить.

### Атака "обиженки": временная стоимость мести

**Сценарий:** злоумышленник хочет навредить конкретному пользователю — отказать в restore, когда тому реально понадобится.

Почему это **значительно сложнее**, чем кажется:

1. **Инвестиция времени.** Нужно набрать репутацию — месяцы реального хранения чужих данных, включая данных жертвы. Всё это время злоумышленник **реально тратит своё место и bandwidth.**

2. **Ожидание события.** Атака "срабатывает" только когда у жертвы **реально умрёт диск** и понадобится restore. Это может не случиться годами. Злоумышленник годами хранит данные жертвы, ожидая момента.

3. **Один из многих.** При erasure coding 5-of-15, жертве нужно лишь 5 шардов из 15. Один злоумышленный пир отказал — осталось 14. Для реального ущерба нужно контролировать ≥11 из 15 шардов, что требует 11 sybil-нод, **каждая с месяцами/годами репутации.**

4. **ROI = отрицательный.** Годы хранения чужих данных + электричество + bandwidth → ради вероятности, что одна из 15 копий не вернётся в момент, который может не наступить.

```
Типичный сценарий:
- Злоумышленник хранит 10 ГБ шардов жертвы 2 года
- Жертва теряет диск на 3-й год
- Жертва запрашивает restore
- Злоумышленник отказывает
- Жертва получает данные от 14 других пиров
- Итог: злоумышленник потратил 2 года → нулевой эффект
```

**Вывод:** таргетированная атака требует ресурсов, несопоставимых с ущербом. Это не уязвимость — это экономическая невыгодность, как Sybil at scale.

## 4.10 Identity = Personal Cluster (не одна нода)

### Ключевой инсайт: пользователь — это не одно устройство

Реальный пользователь приходит в сеть не как одна нода, а как **кластер доверенных устройств:**

```
Identity (master key, seed phrase)
│
├── Laptop      (device key 1, derived)
├── Desktop     (device key 2, derived)
├── NAS         (device key 3, derived)
└── Trusted partner  (device key 4, delegated, revocable)
```

Сеть видит **одну identity** с несколькими device endpoints. Reputation — per identity, shared across all devices. Внутри personal cluster — полное доверие, общий незашифрованный metadata.

### Криптографическая структура

```
Master key (из seed phrase)
├── derives → Device key 1 (laptop) — автоматически
├── derives → Device key 2 (desktop) — автоматически
├── derives → Device key 3 (NAS) — автоматически
└── delegates → Partner key 4 (delegation certificate, revocable)
```

- **Device keys** — детерминированно derived из master key. Компрометация одного устройства → revoke device key, остальные не затронуты.
- **Partner keys** — delegated явным действием. "Я доверяю этому человеку как себе." Revocable в любой момент.
- **Сеть верифицирует:** подписи device keys через связь с master key. Одна reputation, несколько endpoints.

### Два слоя metadata

Это решает фундаментальный trade-off "privacy vs. autonomous repair":

```
┌─────────────────────────────────────────┐
│     Personal cluster (UNENCRYPTED):     │
│  - Полная карта шардов                  │
│  - Ключи шифрования файлов             │
│  - Все device keys                      │
│  - Любое устройство может:              │
│    repair, restore, verification        │
└─────────────────────────────────────────┘

┌─────────────────────────────────────────┐
│     External peers (ENCRYPTED):         │
│  - Opaque blob                          │
│  - Пир не знает что хранит              │
│  - Не может repair, только хранить      │
└─────────────────────────────────────────┘
```

**Внутри** — полная прозрачность: каждое устройство знает всё. **Снаружи** — полная приватность: чужие пиры видят только opaque blobs.

### Какие проблемы это решает

**Autonomous repair (бывшая дыра):**
NAS имеет незашифрованный metadata → знает полную карту шардов. Пир ушёл → NAS сам инициирует repair: скачивает k живых шардов → восстанавливает потерянные → раскладывает по новым пирам. **Владелец не нужен.** Encrypted metadata для external peers не мешает — NAS работает с unencrypted копией.

**"Сел в тюрьму" (6.3) — решено:**
NAS дома always-on. Владелец отсутствует 2 года. NAS:
- Отвечает на proof-of-storage challenges → reputation жива
- Мониторит shard-holding peers → repair при churn
- Хранит чужие шарды → "платит взносы"
- **Данные живы без участия владельца, неограниченно**

Даже без NAS: если desktop остался дома включённым, или trusted partner имеет свою ноду — та же функция.

**Bootstrap — усилен:**
4 своих устройства = 4 ноды, contributing storage с day 1. Совокупный storage contribution = 4× → быстрый набор reputation для identity.

**"Работает для двоих" — буквально:**
Даже без сети: laptop + NAS = локальная redundancy (как Syncthing, но с шифрованием и versioning). Добавил desktop = три копии. Добавил trusted partner = четыре. **Каждый шаг ценен до подключения к open network.**

### Trusted partner = delegation, не второй аккаунт

"Доверенный партнёр" (друг, родственник, коллега) — это delegation certificate с ограниченными полномочиями:

| Полномочие | Device key (своё устройство) | Partner key (доверенный) |
|---|---|---|
| Хранить шарды | Да | Да |
| Видеть metadata | Да | Да |
| Инициировать repair | Да | Да |
| Выполнить restore | Да | Да (если разрешено) |
| Менять master key | Нет (нужен seed) | Нет |
| Revoke других | Нет | Нет |
| Быть revoked | Да | Да |

Partner key = встроенный в архитектуру "хранитель" (custodian), не добавленный сбоку mechanism.

### Own nodes не расходуют "квоту" сети

Шард на своём NAS — это не нагрузка на чужие ноды. Протокол различает:
- **Internal shard** (на своей ноде) — бесплатно для сети, не расходует social capital
- **External shard** (на чужой ноде) — расходует reputation/quota

Юзер может хранить 100% данных на своих устройствах + erasure-coded копию в сети для disaster recovery. NAS как "горячий" слой (быстрый restore), сеть как "холодный" (если NAS сгорел).

### Ценность с первого дня: порядок между устройствами

До подключения к сети personal cluster уже решает реальную проблему: **у большинства людей бардак между устройствами.** Фото на телефоне, документы на ноутбуке, часть на desktop, что-то на старом ноутбуке в шкафу. Нет единой картины, нет уверенности что важное не потеряется при смене устройства.

Personal cluster с shared metadata = **единый каталог всех данных** across all devices:
- Вижу все свои файлы со всех устройств в одном месте
- Знаю что документы есть и на ноутбуке, и на NAS
- Знаю что фото с телефона автоматически попали на desktop
- При замене устройства — просто добавляю device key, данные подтягиваются

Это не "бекап когда-нибудь пригодится" — это **ежедневная польза**: порядок, видимость, уверенность. Бекап в сеть — бонус сверху.

### Migration path

```
Шаг 0: Один ноутбук. Нет бекапа, бардак. (большинство людей сейчас)
Шаг 1: Ноутбук + NAS. Единый каталог, локальный sync. Порядок.
Шаг 2: + desktop + старый ноутбук. Personal cluster, 4 копии.
        Все данные видны отовсюду, смена устройства безболезненна.
Шаг 3: + trusted partner (partner key). Offsite backup у доверенного.
Шаг 4: Подключились к open network. Erasure coding в сеть.
       Disaster recovery от пожара/кражи/тюрьмы.

Каждый шаг — больше порядка и защиты. Тот же протокол на каждом шаге.
```

### Обновлённая таблица trust levels

| Уровень | Кто | Verification | Metadata | Restore |
|---|---|---|---|---|
| **Self** | Свои устройства (device keys) | Не нужна | Unencrypted | Мгновенный |
| **Partner** | Доверенные (delegated keys) | Не нужна | Unencrypted | Мгновенный |
| **Inner** | Стабильные пиры в кластере | Раз в неделю | Encrypted | По trust level |
| **Outer** | Пиры из других кластеров | Раз в день | Encrypted | По trust level |
| **Stranger** | Новички | Каждые 4 часа | Encrypted | Gated |

## 4.11 Управление дисковым пространством: эластичность, ранги, предсмертный крик

### Принцип: программа — гость на диске пользователя

Нельзя заставлять пользователя "отдать 50 ГБ навсегда." Диск — его, не наш. Программа занимает **процент от свободного места** (по умолчанию ~90% свободного) и **дышит** вместе с диском:

```
Свободно 500 ГБ → программа использует ~450 ГБ под чужие шарды
Скачал фильм 30 ГБ → свободно 470 → программа сжалась до ~423 ГБ
Удалил фильм → свободно 500 → программа расширилась обратно

Пользователь никогда не думает "мне не хватает места из-за этой программы."
```

Настраиваемые параметры (user policy, не протокол):
- Процент свободного места (default 90%)
- Абсолютный минимум свободного (default 10 ГБ — "неснижаемый остаток")
- Абсолютный максимум под программу (например, 500 ГБ на диске в 2 ТБ)

### Ранги шардов (eviction priority)

Когда место сжимается — программа должна решить, что удалять первым. Каждый хранимый шард получает **ранг удаления** на основе нескольких факторов:

**Удаляются первыми (низкий ранг):**
- Шарды от пиров с низкой репутацией (PID score < порога)
- Шарды с высокой redundancy у хозяина (14 из 15 копий живы — потеря одной некритична)
- Старые шарды без свежей верификации (хозяин давно не проверял)
- Шарды от пиров, которые не хранят ничего нашего (нет взаимности)

**Удаляются последними (высокий ранг):**
- Шарды от партнёров и пиров с высокой репутацией
- Шарды с критической redundancy (осталось 6 из 15 — каждая копия на вес золота)
- Свежие шарды с подтверждённой верификацией
- Шарды от пиров, хранящих наши данные (взаимность)

Формула ранга — взвешенная комбинация, вычисляется локально. Конкретные веса — user policy, протокол определяет только входные переменные.

### Commitment levels: "храню надёжно" vs "могу удалить"

Каждый пир сообщает хозяину шарда текущий **уровень обязательства**:

| Level | Значение | Когда |
|---|---|---|
| **Stable** | Храню, место есть, удалять не планирую | Нормальный режим |
| **Pressured** | Место сжимается, шард в зоне риска | Ранг шарда низкий, диск заполняется |
| **Evicting** | Удаляю через N часов, перемести шард | Конкретный deadline |

Переход Stable → Pressured → Evicting даёт хозяину **время среагировать**: найти другого пира, повысить redundancy, поднять свою репутацию. Не внезапная потеря, а предупреждение.

### Graceful degradation при нехватке места

```
Место уменьшается
  → Программа сжимает storage pool
  → Шарды с низким рангом переводятся в статус Pressured
  → Хозяевам отправляются уведомления
  → Если место продолжает уменьшаться: Pressured → Evicting (с deadline)
  → Хозяин ищет замену, repair запускается
  → Шард удаляется после deadline или когда хозяин подтвердил перемещение
```

Критично: **никогда не удалять без предупреждения.** Даже если осталось 100 МБ — программа уведомляет, ждёт deadline, и только потом удаляет. Внезапная потеря шарда — то, от чего мы защищаем, а не то, что мы делаем.

### "Предсмертный крик" (graceful shutdown)

При удалении программы или выключении хранения:

1. **Broadcast всем пирам:** "я ухожу, все мои шарды будут потеряны через N часов"
2. **Каждый затронутый хозяин:** получает список шардов, которые потеряет → запускает repair
3. **Программа ждёт** (если возможно): даёт время на repair перед фактическим удалением
4. **Если не дождались** (force uninstall): шарды просто пропадают — но все уже уведомлены

Это радикально лучше, чем внезапное исчезновение. Repair по уведомлению — часы. Repair по обнаружению через proof-of-storage — дни/недели.

**Аналогия:** сосед продаёт дом, но за месяц до этого говорит "заберите свои вещи из моего гаража." Не выбрасывает молча.

### Влияние на репутацию

- **Graceful eviction** (предупредил → дал время → удалил): репутация не страдает, это нормальное поведение
- **Graceful shutdown** (предсмертный крик): репутация замораживается на текущем уровне, accumulated I сохраняется при возвращении
- **Silent disappearance** (ушёл без предупреждения): PID D-компонент фиксирует резкое падение, репутация падает
- **Eviction + не хранил** (proof-of-storage fail после eviction): самый серьёзный удар по репутации

Протокол **поощряет честность**: лучше сказать "у меня мало места" и потерять один шард по плану, чем молча потерять десять.

## 4.12 Умное ранжирование данных: ML как killer feature

### Проблема: не все гигабайты одинаковы

Типичный пользователь думает: "у меня 500 ГБ фото, бекапить долго и дорого." Реальность — из 500 ГБ **незаменимых** может быть 30-50 ГБ. Остальное: дубли, технический брак, скачанные мемы, скриншоты, серии из 40 одинаковых кадров.

Тройка документы/фото/видео — грубое приближение. ML на стороне клиента позволяет **автоматически оценить ценность каждого файла** до отправки в сеть.

### Что умеет оценивать ML (локально, на клиенте)

**Документы — не все одинаково ценны:**
| Тип | Ценность | Почему |
|---|---|---|
| Свой текст, заметки, проектные файлы | Высокая | Невоспроизводимы |
| Конфиги, dotfiles | Средняя | Воспроизводимы, но муторно |
| Скачанные книги, PDF | Низкая | Можно скачать снова |
| Кеши, node_modules, .git | Нулевая | Не бекапить |

**Фото — ранжирование внутри коллекции:**
| Сигнал | Действие |
|---|---|
| Уникальный кадр, люди, события | Высокий приоритет |
| Серия похожих (37 фото ужина) | Оставить лучшие 3-5, остальные — низкий приоритет |
| Технический брак (blur, пересвет, палец) | Предложить не бекапить |
| Скриншоты, мемы | Низкий приоритет |
| Архив: фото 2015 года | **Выше** чем вчерашние (невоспроизводимо!) |

**Видео — самый большой выигрыш:**
| Тип | Ценность | Объём |
|---|---|---|
| Семейное видео, уникальное | Высокая | Бекапить полностью |
| Скачанный фильм/сериал | Нулевая | Не бекапить (можно скачать) |
| Запись экрана, созвоны | Низкая | С минимальной redundancy |

### Ключевой инсайт: архив жизни важнее вчерашних фото

Обычная логика: "новое = важное." Правильная логика для бекапа — **обратная:**

```
10 фото из 2015 — незаменимы. Негде взять второй раз.
200 фото с прошлой недели — потеря переживаема.
Видео первых шагов ребёнка (2018) — бесценно.
Видео вчерашнего ужина — nice to have.
```

ML может автоматически поднять приоритет **старых файлов без дублей** и понизить **свежих файлов с высокой redundancy** (есть на телефоне, на ноутбуке, в мессенджере).

### Влияние на систему

**1. Уменьшает реальный объём бекапа в 5-10 раз.**
Вместо "бекапим 500 ГБ" → "бекапим 50 ГБ незаменимого с высокой redundancy, 150 ГБ ценного со стандартной, 300 ГБ заменимого — не бекапим или с минимальной."

**2. Instant value с первого запуска — до подключения к сети.**
Пользователь устанавливает программу и сразу видит:
- "У тебя 47 ГБ незаменимых данных из 500 ГБ"
- "Вот 2000 дублей фото — хочешь удалить и освободить 15 ГБ?"
- "Вот 80 ГБ скачанных фильмов — бекапить не нужно"
- "Фото 2015-2018 — 12 ГБ без единой копии, это красная зона"

Это **ценность до первого шарда**, как personal cluster с порядком между устройствами.

**3. Превращает тиры из трёх в спектр.**
Не три фиксированных класса (документы/фото/видео), а непрерывный ранг ценности. Erasure coding параметры (k-of-n) привязываются к рангу:

```
Ценность 0.9-1.0: 3-of-20  (документы, старые уникальные фото)
Ценность 0.6-0.9: 5-of-15  (хорошие фото, личные видео)
Ценность 0.3-0.6: 6-of-10  (средние фото, рабочие видео)
Ценность 0.0-0.3: не бекапить или 8-of-10 (скачанное, дубли, брак)
```

### Не на уровне протокола

Важно: ML-ранжирование — **фича клиента**, не протокола. Протоколу всё равно, почему конкретный файл получил конкретный tier. Пользователь может:
- Полностью положиться на автоматику
- Корректировать ранги вручную ("это фото важнее чем ML думает")
- Отключить ML и вернуться к ручной тройке документы/фото/видео

Протокол видит только: "этот шард — tier X с параметрами k-of-n." Откуда взялся tier — не его дело.

### Реализация: не нужна своя модель

Не нужно обучать ML с нуля. Готовые компоненты:
- **Дубли фото:** perceptual hashing (pHash, dHash) — библиотеки, не ML
- **Качество фото:** CLIP, предобученные модели оценки — inference локально
- **Классификация файлов:** по расширению + magic bytes + размер — правила, не ML
- **Семантическая группировка:** CLIP embeddings → кластеризация → "событие" (все фото ужина = один кластер)
- **Определение скачанного:** размер + metadata + отсутствие EXIF → вероятно не оригинал

Всё работает **локально**, ничего не уходит в сеть. Privacy сохраняется полностью.

### Последний рубеж: умное сжатие

Когда места совсем мало — перед тем как отказываться от бекапа, можно **сжать без потери смысла:**

**Фото:** большинство фото содержит значительно меньше информации, чем весит файл. 12-мегапиксельный JPEG семейного ужина на 8 МБ несёт ту же эмоциональную и архивную ценность при 2 МБ. ML может определить:
- Фото с мелкими деталями (документ, карта, чертёж) → не сжимать
- Фото "момент жизни" (люди, события, пейзажи) → можно сжать 3-4x без заметной потери
- Скриншоты → PNG→JPEG, выигрыш 5-10x

**Видео:** перекодирование из старых кодеков (H.264) в современные (AV1/H.265) может уменьшить объём на 40-60% при том же визуальном качестве.

Важно: сжатие — **последний рубеж**, не первый. Приоритет:
```
1. Не бекапить ненужное (скачанное, дубли, мусор)     — бесплатно
2. Снизить redundancy для менее ценного                 — бесплатно
3. Сжать то, что можно сжать без потери смысла          — CPU cost
4. Отказаться от бекапа наименее ценного                — крайний случай
```

Пользователь всегда контролирует: "сжимать фото — да/нет", "минимальное качество — N%". ML предлагает, человек решает.

# Часть V. Строительные блоки (pluggable, заменяемое)

## 5.1 Транспорт: iroh

**Лучший выбор для home users behind NAT.**

| Характеристика | Значение |
|---|---|
| Язык | Rust |
| Зрелость | v0.96.1 (март 2026), близко к 1.0 |
| Stars | ~7,900 |
| Real-world usage | ~500,000 unique nodes за 30 дней |
| NAT traversal | ~70% direct (QUIC hole punching), остальное через relay |
| Relay | Always works, n0 runs public relays (US/EU/Asia), open-source relay можно поднять свой |
| Blob transfer | iroh-blobs: BLAKE3-verified streaming, от КБ до ТБ |
| Identity | Public key based (Ed25519), не IP-адреса |

**Преимущества:**
- "Просто работает" за домашними NAT
- iroh-blobs — готовый verified blob transfer (наш основной примитив)
- Relay всегда доступен как fallback
- API проще чем libp2p

**Риски:**
- Pre-1.0 API instability — pin to specific version
- Зависимость от n0.computer relay infrastructure (mitigated: relay open-source, можно свой)

### Альтернативы (если iroh не подходит)

- **go-libp2p** — production-grade, но сложнее. Circuit Relay v2 ограничен (128KB/2min). Подходит если проект на Go.
- **Mainline BitTorrent DHT** — для peer discovery (20 лет в бою), но это только discovery, не transport.

## 5.2 Erasure Coding

### Rust: reed-solomon-simd

- Самый быстрый в бенчмарках на AMD Ryzen
- GF(2^16) — до 32,768 original + 32,768 recovery shards
- Runtime SIMD selection: AVX2/SSSE3/NEON/fallback
- Actively maintained

### Go: klauspost/reedsolomon

- De facto standard, ~2,000 stars
- >1 GB/s на ядро в pure Go, до 3x быстрее с GFNI (AVX-512)
- Используется: Apache Hadoop, Azure, Facebook cold storage, Backblaze
- Battle-tested at planetary scale

### Рекомендуемые параметры

| Сценарий | Shards | Параметры | Overhead | Peer failures tolerated |
|---|---|---|---|---|
| Tier 1 (документы) | 15 | 5-of-15 | 3x | 10 |
| Tier 2 (фото) | 10 | 4-of-10 | 2.5x | 6 |
| Tier 3 (видео) | 10 | 6-of-10 | 1.7x | 4 |

**Скорость:** 200 ГБ при 1 ГБ/с = ~200 секунд single-threaded. Multi-core: ~25 секунд. Вполне приемлемо для домашнего бекапа.

### Fountain codes — не нужны

Reed-Solomon выигрывает для нашего use case: точно известный overhead, зрелые реализации, deterministic recovery. Fountain codes (LT/Raptor) дают probabilistic recovery — лишняя сложность без выгоды когда peer count известен.

## 5.3 Шифрование

### Схема: encrypt-then-split

```
file → encrypt with XChaCha20-Poly1305 → ciphertext + auth tag
ciphertext → Reed-Solomon encode → shards
shards → distribute to peers
```

**Восстановление:**
```
≥k shards → Reed-Solomon decode → ciphertext
ciphertext → decrypt → file
```

### Почему encrypt-then-split, а не split-then-encrypt

1. Один ключ шифрования на файл (не на шард)
2. Один authentication tag на весь plaintext
3. Каждый шард — opaque blob
4. Пир не может извлечь даже частичную информацию из одного шарда

### Алгоритм: XChaCha20-Poly1305 (libsodium)

- 192-bit random nonces — безопасно генерировать случайно, практически нет лимита на количество сообщений
- Authenticated encryption (confidentiality + integrity)
- Libsodium — bindings для каждого языка
- Для Rust: `chacha20poly1305` из RustCrypto или `ring`

### НЕ использовать: convergent encryption

Tahoe-LAFS использует convergent encryption (`key = H(convergence_secret || file_contents)`) для дедупликации. Для нашей системы это **вредно**: позволяет confirmation-of-file attack (проверить есть ли у юзера конкретный файл). Дедупликация между юзерами не нужна — используем случайные ключи.

## 5.4 Content Hashing: BLAKE3

- ~3 ГБ/с single-threaded (vs SHA-256 ~0.65 ГБ/с)
- Multi-threaded: ~15.8 ГБ/с (exploits internal Merkle tree parallelism)
- Используется iroh-blobs для verified streaming
- Production-ready

## 5.5 Peer Discovery: Mainline BitTorrent DHT

Для начального обнаружения пиров — 20-летний battle-tested DHT с миллионами нод.

**Go:** `anacrolix/dht` (production since 2014)
**Rust:** `pubky/mainline` (v6.1.1, февраль 2026). Поддерживает BEP44 — mutable signed key-value storage.

**BEP44 для metadata pointer:** Mutable items подписаны Ed25519. Ограничение: 1000 байт — достаточно для указателя на полный metadata blob.

### Внутри кластера: gossip, не DHT

Для closed cooperative (10-15 known peers) публичный DHT не нужен для metadata. Простой gossip protocol между пирами кластера + DHT как bootstrap/fallback.

## 5.6 Proof of Storage: Merkle-tree challenges

Нет готовых библиотек — реализуется самостоятельно, но просто.

Полный асинхронный протокол описан в разделе 4.7 — включая relay-модель, anti-collusion свойства, и PID-репутацию "почтальонов."

### Реализация

1. При upload: разбить шард на блоки (256 КБ), построить Merkle tree (BLAKE3), сохранить **только root** (32 байта) в metadata
2. Challenge: подписанный запрос {nonce, block_index} → relay → пир
3. Response: подписанный ответ {block_data, merkle_proof} → relay → верификатор
4. Verify: hash(block_data) → merkle_proof → root match?

### Costs

| Метрика | Значение |
|---|---|
| Verification data per shard | 32 байта (Merkle root) |
| Challenge-response size | ~257 КБ (block + proof + signatures) |
| Per-week (10 shards) | ~2.5 МБ |
| Computational cost | Микросекунды (BLAKE3 hash + proof check) |
| Требует одновременный online | Нет (async через relay) |

# Часть VI. Открытые вопросы

## 6.1 (перенесён в раздел 4.10)

## 6.2 Shard migration coordination

Когда пир уходит, его шарды нужно перераспределить. Кто координирует? В кластере — gossip protocol, но нужен consensus "пир X мёртв, начинаем repair." Варианты:
- Простой timeout: 14 дней offline → считаем мёртвым
- D-компонент reputation: тренд резко вниз → превентивный repair, не дожидаясь timeout
- Каждый пир решает сам (как в GNUnet) — нет координации, возможна избыточная re-replication

## 6.2 Версионирование документов

Фото иммутабельны — записал и забыл. Документы меняются. Варианты:
- Append-log: каждая версия — отдельный snapshot, независимо бекапится
- Content-addressed dedup: если изменилось 5% документа, только delta нужна
- Простой подход: при каждом backup cycle создаём snapshot изменившихся документов (они маленькие — overhead минимален)

## 6.3 "Сел в тюрьму": долгое отсутствие после потери устройства

**Сценарий:** юзер потерял устройство (конфискация, кража, пожар) и не может вернуться в сеть 6-24 месяца. Seed phrase сохранена (бумажка в сейфе). Но юзера нет — он не может ни верифицировать, ни обновлять metadata, ни "платить взносы."

**Проблема:** за 6-24 месяца без присутствия владельца:
- Часть shard-holding пиров уйдёт (churn)
- Repair невозможен — владелец не инициирует
- Оставшиеся пиры не знают: владелец вернётся или нет
- Шарды занимают место → пиры хотят освободить → давление на удаление

**Что происходит без специального механизма (только математика):**

При 4-of-10 erasure coding, допустим annual churn rate = 30% (30% пиров уходят за год):
- Через 6 мес: ~15% пиров ушло → ~1.5 из 10 шардов потеряно → ОК (нужно 4)
- Через 12 мес: ~30% → ~3 из 10 → ОК (нужно 4, осталось ~7)
- Через 18 мес: ~45% → ~4.5 из 10 → на грани (нужно 4, осталось ~5.5)
- Через 24 мес: ~60% → ~6 из 10 → скорее всего потеря (осталось ~4, ровно на грани)

Для tier 1 (документы, 5-of-15): через 24 мес при 30% churn → ~9 из 15 живы → ОК (нужно 5).

**Вывод: для документов (tier 1 с высоким redundancy) математика может хватить на 2+ года. Для фото (tier 2) — ~18 месяцев на грани.**

**Возможные механизмы усиления (для проработки):**

### Вариант A: "Хранители" (Custodian peers)

Владелец назначает 2-3 "хранителя" (друг, родственник, адвокат) которые имеют **ограниченные полномочия:**
- Могут инициировать repair (перераспределить шарды на новые пиры)
- НЕ могут читать данные (не имеют ключа шифрования)
- НЕ могут выполнить restore (только repair)
- Авторизованы подписанным delegation certificate от владельца

Хранитель видит: "3 из 10 шардов потеряны, инициирую repair." Скачивает 4 живых шарда → восстанавливает 3 потерянных → раскладывает по новым пирам. Данные остаются зашифрованными — хранитель работает с opaque blobs.

**Вопрос:** хранитель должен оплатить repair "репутацией"? Или repair от имени absent owner — бесплатный? Или owner заранее "депонирует" reputation (хранит чужие шарды с запасом)?

### Вариант B: Автономный repair протокол

Shard-holding пиры **сами** инициируют repair когда видят что владелец долго offline:
- Пир A хранит шард S1. Видит что пир B (хранивший S2) ушёл.
- Пир A знает (из encrypted metadata? нет — metadata зашифрована, пир не знает других shard holders).
- **Проблема:** без metadata пиры не знают друг о друге. Только владелец знает полную картину.

**Вывод:** автономный repair без хранителя невозможен при encrypted metadata. Нужна либо частичная metadata (список shard holders, но не содержимое файлов), либо хранитель.

### Вариант C: "Reputation deposit" — запас хранения

Владелец заранее хранит для сети **больше** чем нужно. Запас "купленного времени":
- Хранишь 200 ГБ для других, бекапишь 100 ГБ → deposit = 100 ГБ
- Deposit "сгорает" постепенно пока ты offline (другие пиры реклассифицируют тебя как inactive)
- При 100 ГБ deposit и стоимости repair ~50 ГБ bandwidth → deposit хватает на ~2 года

**Вопрос:** кто тратит deposit? Пиры делают repair "в долг" absent owner-у?

### Вариант D: Увеличение начального redundancy для tier 1

Простейшее решение: документы (5 ГБ) с redundancy 3-of-20 вместо 5-of-15.
- 20 шардов, нужно 3 для восстановления
- Через 24 мес при 30% churn: 8 из 20 живы → ОК (нужно 3)
- Через 36 мес: ~6 из 20 живы → ОК
- Через 48 мес: ~4 из 20 → ОК
- Overhead: ~6.7x для 5 ГБ = 33 ГБ на сети = ~1.6 ГБ на пира. **Ничтожно.**

Для документов (крошечных, критичных) это может быть достаточно: просто дать столько redundancy, чтобы математика работала на 5+ лет без repair.

**Предварительный вывод:** для данной задачи комбинация D (massive redundancy для мелких критичных данных) + A (хранители для крупных) выглядит наиболее реалистичной. Чистая математика работает для документов; для фото нужен mechanism.

## 6.4 DHT metadata persistence

Частично решено в разделе 4.6 (encrypted metadata everywhere + anchor peers). Оставшийся вопрос: как пиры republish-ат DHT-записи за absent owner?

Решение: пир, хранящий encrypted metadata, периодически republish-ает её в DHT по public key владельца. Не требует знания содержимого — просто "вот blob, вот ключ для lookup, вот подпись." Пока хоть один shard-holding пир жив — DHT-запись жива.

## 6.4 Peer selection for geographic diversity

**Проблема:** органические кластеры тяготеют к географической однородности (похожий timezone = похожий online schedule = стабильная связь). А disaster recovery требует обратного.

**Частичное решение через bootstrap dynamics:** новички с trust = 0 не имеют выбора — берут тех партнёров, которые доступны. "Мне никто не верит, тебе никто не верит — давай дружить." Новичок из Москвы + новичок из Берлина → партнёрство → кластер с geographic diversity **как побочный эффект bootstrap.** Ранние кластеры формируются не по географии, а по времени прихода.

По мере роста сети новые ноды продолжают появляться и сбиваться в федерации. Разнообразие поддерживается естественным притоком.

**Оставшиеся вопросы для балансировки (на потом):**
- Как определить geography без центрального сервера? Latency measurements + self-reported timezone
- Нужен ли явный "diversity score" при shard placement?
- Mature network: как предотвратить географическую гомогенизацию кластеров со временем?

## 6.5 UX: что видит пользователь

Критично для adoption. Минимальный viable UX:
1. Установить приложение
2. Выбрать папки для бекапа
3. Выделить место для хранения чужих данных
4. Dashboard: "ваши данные защищены на X%", "вы храните Y ГБ для других", "репутация: Z"
5. Restore: выбрать файлы → подождать (дни) → получить

## 6.6 Экономика хранения в числах

Сеть из 1000 пользователей, каждый:
- Бекапит 100 ГБ (средний)
- Выделяет 300 ГБ (средний)
- Общий бекап: 100 ТБ
- С erasure coding (средний overhead 2.5x): 250 ТБ нужно хранить
- Общее выделенное: 300 ТБ
- **Запас: 50 ТБ (17%).** Хватает с запасом.

При 10,000 пользователей:
- 1 ПБ бекап → 2.5 ПБ с erasure coding
- 3 ПБ выделено
- **Запас: 500 ТБ (17%).** Масштабируется линейно.

## 6.7 Enforce restore gate: verification vs. restore протоколы

**Проблема:** "upload сразу, restore после доказательства ценности" — но что физически мешает новичку скачать свои шарды? Данные зашифрованы его ключом, metadata у него.

**Ответ:** restore и verification — разные протоколы. Verification = 1 случайный блок в неделю (rate-limited). Чтобы "скачать под видом verification" шард 1 ГБ (4000 блоков по 256 КБ) — нужно 4000 недель ≈ 77 лет. Restore = запрос полного шарда, gated by trust score.

**Нужно зафиксировать в протоколе:**
- Verification requests rate-limited (1 block/shard/week)
- Restore — отдельный message type, пир проверяет trust level запрашивающего перед отдачей полного шарда
- Пир ОБЯЗАН отказать в restore при trust ниже порога (это consensus rule протокола, не optional policy)

## 6.8 PID-метафора: формализация для paper/RFC

PID-контроллер: `u(t) = Kp*e(t) + Ki*∫e(t)dt + Kd*de/dt` — P/I/D складываются с весами. В нашей системе P, I, D — три метрики с **разными единицами** (ratio, ГБ·дни, Δ%/месяц), не складывающиеся в одну формулу естественным образом.

Для объяснения концепции аналогия PID работает отлично. Для формальной спецификации (paper, RFC) лучше описать как **multi-timescale reputation score:**
- Short-term signal (current state, window = 1 week)
- Long-term signal (accumulated history, monotonically growing)
- Trend signal (rate of change, window = 30-90 days)

Три сигнала управляют **разными решениями**, а не складываются в одно число:
- Short-term → "отвечать ли на challenge прямо сейчас"
- Long-term → "доверять ли tier 1 шарды"
- Trend → "начинать ли превентивный repair"

## 6.9 Ransomware protection

**Сценарий:** компьютер юзера заражён ransomware. Все файлы зашифрованы вирусом. Клиент Viaticum видит "изменённые документы" → бекапит вирусные версии.

**Для фото:** не проблема. Фото иммутабельные, append-only. Старые шарды не затрагиваются. Новые "фото" (зашифрованные вирусом) добавятся, но старые останутся.

**Для документов:** проблема. Если версионирование перезаписывает старые версии — хороший бекап заменён вирусным.

**Решение:** append-only log для ВСЕХ тиров:
- Старые версии **никогда не удаляются автоматически**
- Удаление старых версий — только явное действие юзера (с подтверждением, с задержкой 7 дней)
- При restore: юзер видит timeline версий и выбирает pre-ransomware snapshot
- Протокол: "delete old version" = отдельный message type с обязательной задержкой

## 6.10 Disk failure vs. churn: различие для reputation

**Сценарий:** пир online, но диск сдох. Шарды потеряны. Пир не ушёл — машина работает. Proof-of-storage challenge failed.

**Проблема:** в текущей модели P = 0 (шарды потеряны), D резко отрицательный → punishment. Но пир честен — не дефектировал, а пострадал.

**Нужно различать:**
- "Silently stopped responding" (потенциально malicious) → reputation hit
- "Honestly reported data loss" (disk failure, честное сообщение) → reduced penalty

**Возможный механизм:** пир при disk failure отправляет signed "data_loss_report" с описанием (какие шарды потеряны). Это:
- Триггерит немедленный repair (не ждём 14 дней)
- Снижает reputation penalty (I сохраняется частично, D penalty мягче)
- Пир остаётся в сети и может сразу начать принимать новые шарды на новый диск

Без этого механизма: пир с disk failure получает такой же punishment как malicious node → несправедливо → пир уходит навсегда → потеря хорошего участника.

## 6.11 "User defines policy" — interoperability edge cases

**Проблема:** если юзер A настроил "храню только для пиров с I > 1000", а юзер B — новичок с I = 0, то A не будет хранить для B, но B может хранить для A. Асимметрия.

При разных политиках у разных юзеров matching (кто хранит для кого) становится multi-constraint optimization problem. В extreme case: все ветераны настроили "только для ветеранов" → новичкам негде хранить → bootstrap сломан.

**Mitigation:**
- Reference implementation defaults: умеренные thresholds, не элитистские
- Обязательный "newcomer quota": каждый пир должен принимать минимум N% шардов от newcomers (часть протокола, не policy)
- Или: newcomer shards оплачиваются "залогом" (storage deposit) → принимающий пир не рискует

## 6.12 "Работает для двоих" — уточнение

При 2 пирах: erasure coding невозможен (только 1-of-2 = полная реплика). Trust protocol не нужен (знаешь друга лично). Получается просто encrypted sync.

Это не баг — полезно на каждом шаге:
```
2 пира:   encrypted sync (как Syncthing с шифрованием)
5 пиров:  erasure coding включается, trust protocol начинает работать
10 пиров: полноценная система с кластерами
50+ пиров: federation, cross-cluster storage
```

Нужно быть честным в документации: "trust protocol — core value проекта — включается при ~5+ пирах." При 2-4 пирах система полезна, но как простой encrypted backup, не как trust network.

# Часть VII. Почему именно сейчас

## 7.1 Что изменилось с 2003 года (Samsara)

1. **Диски подешевели радикально.** В 2003 — 1 ГБ стоил ~$1. В 2026 — ~$0.01. 200-500 ГБ свободного места — норма.
2. **Домашний интернет стал быстрее.** 10-50 Mbps upload — типично. Initial backup 100 ГБ — за сутки, не за месяц.
3. **Библиотеки P2P созрели.** libp2p, iroh, Reed-Solomon implementations — production-grade, не research prototypes.
4. **NAT traversal стал надёжнее.** QUIC, ICE, hole punching — 70% direct connections. В 2003 — значительно хуже.
5. **Crypto primitives доступнее.** XChaCha20, BLAKE3 — быстрые, безопасные, с bindings для всех языков.
6. **Mobile не обязателен.** В 2011 Wuala убило то, что P2P клиент убивал батарею. Наш подход — десктоп/ноутбук. Lazy sync раз в неделю. Не нужен background daemon 24/7.

## 7.2 Почему "холодный бекап" — ключевой инсайт

Все предшественники пытались конкурировать с облаком по скорости и доступности. Это проигрышная позиция — P2P сеть домашних компьютеров не может дать SLA датацентра.

"Холодный бекап" выходит из конкуренции:
- **Не конкурирует с Dropbox** (тот sync, мы backup)
- **Не конкурирует с S3** (тот API + SLA, мы "коробка у родителей")
- **Конкурирует с "ничем"** — подавляющее большинство людей не бекапит вообще. Конкурент — потеря данных, не облако.

# Приложение B. Глоссарий

| Термин | Определение |
|---|---|
| **Erasure coding** | Метод кодирования данных так, что любые k из n частей достаточны для восстановления оригинала |
| **Reed-Solomon** | Конкретный алгоритм erasure coding, основанный на полиномиальной интерполяции в конечных полях |
| **Shard** | Один fragment erasure-coded данных, хранимый у конкретного пира |
| **Churn** | Процесс присоединения и ухода нод из P2P сети |
| **Repair** | Процесс восстановления потерянных шардов на новых нодах |
| **Tit-for-tat** | Стратегия "я делаю для тебя то, что ты делаешь для меня" |
| **Sybil attack** | Создание множества фейковых идентичностей для манипуляции системой |
| **DHT** | Distributed Hash Table — распределённая хеш-таблица для peer discovery |
| **NAT traversal** | Техники установления прямого соединения между пирами за NAT |
| **Hole punching** | Конкретная техника NAT traversal через координированные пакеты |
| **PID controller** | Proportional-Integral-Derivative контроллер — модель управления с учётом текущего состояния, истории и тренда |
| **Proof of storage** | Криптографическое доказательство что пир действительно хранит данные |
| **Content-addressed** | Данные адресуются по хэшу содержимого, а не по имени/пути |
| **Cluster** | Группа пиров с высоким взаимным доверием, сформированная органически |
| **Bridge node** | Пир, состоящий в двух кластерах, обеспечивающий cross-cluster storage |
| **Cold backup** | Бекап с медленным доступом (дни-недели), оптимизированный для надёжности, не скорости |
| **GB·days** | Единица измерения накопленного вклада: гигабайты × дни хранения |
| **Eviction** | Плановое удаление шарда из-за нехватки места, с предупреждением хозяина |
| **Commitment level** | Уровень гарантии хранения шарда: Stable → Pressured → Evicting |
| **Death scream** | Broadcast-уведомление всем пирам при удалении программы или уходе из сети |
