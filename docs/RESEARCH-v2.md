*Март 2026 · по результатам серии экспериментов 01-14*

## 1. Проблема v1

Серия 1 (эксперименты 01-14) установила, что формула `trust = 0.5×P + 2.0×I` работает для ранжирования пиров по uptime (Kendall's tau = 0.91, Exp 01), но имеет три структурных дефекта:

**1. Storage blindness (Exp 13).** Формула видит только результат proof-of-storage проверок (онлайн/офлайн), но не объём хранимых данных. Hoarder (90% uptime, 20% storage capacity) ранжируется #2 из 6 архетипов — выше Weekend Warrior, который хранит всё и доступен 3 дня из 7. Kendall's tau = 0.0 — формула не коррелирует с реальной полезностью.

**2. Daily check penalty (Exp 13).** Ежедневные proof-of-storage проверки штрафуют пиров с предсказуемо-периодическим расписанием. Weekend Warrior онлайн 3 дня из 7, но проходит только 43% ежедневных проверок. При этом он ни разу не подводил, когда был онлайн. Проблема в гранулярности: дневная проверка не различает "был офлайн сегодня" и "ушёл навсегда".

**3. D-warning noise (Exp 14).** D-компонент (тренд P) генерирует 55 событий/год при 91% false positive rate. Для автоматического repair trigger — работает (Exp 03: +30% выживаемость). Для отображения пользователю — непригоден.

## 2. Формула v2: PI+S

```
trust = kp × P_weekly + ki × I_weekly + ks × S
```

### Компоненты

**P — текущее состояние (weekly aggregation):**
```
Каждую неделю: прошёл ли пир ≥1 proof-of-storage проверку?
  → weekly_score = 1 (да) или 0 (нет)
P = среднее за последние 4 недели (скользящее окно)
Диапазон: [0, 1]
```

Ключевое изменение: переход от дневной к недельной гранулярности. Weekend Warrior (онлайн 3/7 дней) теперь получает P = 1.0, потому что он проходит проверку каждую неделю. Nomad (50% random ON/OFF) получает P ≈ 0.93 (вероятность не пройти ни одной проверки за 7 дней при 50% daily = 0.5^7 = 0.008). Отличие от дневного P: weekly P различает "периодически доступен" и "ушёл", а не "был сегодня" и "не был".

**I — накопленная история (weekly):**
```
I = сумма всех weekly_score / количество недель с момента первого контакта
Диапазон: [0, 1]
Без decay — никогда не обнуляется
```

Без изменений по сути (кумулятивная средняя), но считается по недельным значениям вместо дневных. I по-прежнему неподделываем: пир с историей 100 недель × 0.95 = 95 успешных недель не может получить этот результат быстрее, чем за 100 реальных недель.

**S — баланс хранения (новый компонент, попарный):**
```
S_AB = GB_B_stores_for_A / max(GB_A_stores_for_B, ε)
Clamp: [0, 2.0]
```

S вычисляется **попарно**, не глобально. Нода A оценивает конкретного партнёра B:
- Числитель: сколько B хранит для A (A верифицирует через PoS — наблюдаемо)
- Знаменатель: сколько A хранит для B (A знает локально)

Примеры:
- S = 1.0 → баланс (B хранит для A столько же, сколько A для B)
- S = 0.2 → Hoarder (B хранит 20% от того, что A хранит для B)
- S = 2.0 → максимальный бонус (B хранит вдвое больше, cap)

Почему попарный, а не глобальный:
- **Наблюдаемость:** A напрямую знает оба значения, не нужен gossip или self-report
- **Неподделываемость:** числитель верифицируется PoS, знаменатель — локальное знание
- **Глобальный S — вектор атаки:** пир может накачать S храня для одних, а потребляя у других; попарный S это исключает
- **Усиливает кластеризацию:** взаимные пары (S ≈ 1.0 у обоих) предпочитаются → стабильные ядра

Следствие для кластеризации: попарный S создаёт давление к взаимности. Пары с симметричным хранением укрепляются, образуют треугольники и кластеры. Это усиливает эффект acceptance gate (Exp 10). Требует проверки в Exp 17: не приводит ли к чрезмерной изоляции кластеров.

### D — repair trigger (без изменений)

```
D = P[this_week] - P[prev_week]
Trigger: 2 подряд недели с D < -0.05
```

D по-прежнему не входит в trust score. Изменение: вместо дневного D с порогом -0.01 используется недельный D с порогом -0.05 и гистерезисом (2 подряд). Ожидаемый результат: снижение FP rate с 91% до ~70%.

### Параметры

```
Лучшая конфигурация (Exp 15, sweep 54 configs, 30 seeds, 5 лет):
  kp = 0.3   (текущее состояние — демпфировано)
  ki = 1.5   (история — доминирует, но чуть слабее чем в v1)
  ks = 0.3   (баланс хранения — даже малый вес достаточен)
```

Робастность: любой ks > 0 при ki ≥ 1.5 даёт tau ≥ 0.83 к месяцу 6 и tau ≥ 0.97 к месяцу 12. Формула не чувствительна к точным значениям параметров — S создаёт категорический разрыв между честными пирами (S ≈ 1.0) и free-riders (S ≤ 0.2).

| Архетип | Реальная полезность | PI rank (v1) | PI+S rank (v2) | Trust v2 |
|---------|:---:|:---:|:---:|:---:|
| Reliable (99% uptime, full storage) | 1 | 1 | **1** | 2.10 |
| Weekend (3/7d online, full storage) | 2 | **5** | **2** | 2.10 |
| Seasonal (summer off, full storage) | 3 | **4** | **3** | 2.02 |
| Nomad (~50% random, full storage) | 4 | 6 | **4** | 1.98 |
| Hoarder (90% uptime, 20% storage) | 5 | **2** | **5** | 1.86 |
| Freeloader (80% uptime, 10% storage) | 5 | **3** | **6** | 1.83 |

Kendall's tau: v1 = **0.0** (случайно), v2 = **0.97** (почти идеально).

### Convergence speed

| Milestone | v1 (PI-only) | v2 (PI+S) |
|-----------|:---:|:---:|
| tau ≥ 0.8 | никогда | месяц 6 |
| tau ≥ 0.9 | никогда | месяц 12 |
| Стабильный ranking | никогда | месяц 12+ |

### Что исправлено

1. **Hoarder/Freeloader:** с rank #2-3 → rank #5-6. S-term видит, что они хранят 10-20% от потребляемого.
2. **Weekend Warrior:** с rank #5 → rank #2. Weekly P не штрафует за предсказуемое расписание.
3. **Seasonal:** с rank #4 → rank #3. I-компонент по-прежнему буферизует летнее отсутствие, weekly P ослабляет штраф.

### Что не изменилось

- Reliable (#1) и Nomad (#4→#4) ранжировались корректно и в v1
- I-компонент по-прежнему доминирует (ki = 1.5 vs kp = 0.3)
- Erasure coding, subnet rate-limiting, acceptance gate — не затронуты

## 4. Кредит доверия (Trust Escrow)

Новый механизм для решения bootstrap problem.

### Проблема

Пользователь пришёл в систему, загрузил 50 ГБ данных, и сразу умер диск. Данные в сети, система может их хранить. Но если отдать сразу — дыра в экономике: загрузил → вытянул → ушёл, сеть потратила ресурсы бесплатно.

### Решение

Не отдаём, но и не стираем. Файлы хранятся в escrow. Пользователь покупает новый диск, хранит чужие данные, набирает I-score — система постепенно разрешает restore.

### Механика

- **Upload** всегда разрешён — данные раскладываются по сети, overhead минимален (шарды уже выделены)
- **Restore** требует минимальный I-score, пропорционально объёму:
  - Tier 1 (документы, < 5 ГБ): I ≥ 0.1 (~1 месяц работы)
  - Tier 2 (фото, < 50 ГБ): I ≥ 0.3 (~3 месяца)
  - Tier 3 (видео, > 50 ГБ): I ≥ 0.5 (~6 месяцев)
- **Авансовый кредит**: первый restore до 1 ГБ бесплатно — демо-эффект, чтобы пользователь увидел, что система работает
- **Partial restore**: документы раньше, видео позже (по tier)

### Экономика

- Стирание штрафует честного невезучего пользователя
- Хранение в escrow стоит почти ничего (~3 ГБ на каждом из 15 хранителей)
- Мощный lock-in: "файлы в безопасности, но нужно заслужить доступ"
- S-term из PI+S усиливает escrow: мало хранишь для других → низкий trust → дольше ждёшь restore

### Обобщение

Trust escrow — обобщение acceptance gate:
- Gate: "не дадим _хранить для тебя_" (protect storage providers)
- Escrow: "не дадим _забрать_" (protect network economy)
- Вместе: gate + escrow = полный цикл защиты от free-riding

## 5. Шаринг доверия: верифицируемые свидетельства

### Текущая модель: полностью локальное доверие

Каждая нода хранит trust score для каждого партнёра, вычисленный только из собственных наблюдений. Никакого обмена репутацией между нодами.

Преимущества:
- Нет глобального консенсуса → нет блокчейна → нет токенов
- Нет вектора "фейковые рекомендации"
- Каждая нода автономна

Проблемы:
- Cold start: каждые отношения строятся с нуля
- Дублирование верификации: если A и B оба работают с C, оба тратят bandwidth
- Потеря устройства: история trust теряется вместе с нодой (Personal Cluster частично решает)

### Trust referral: подпорка для bootstrap, не базовый механизм

Идея: A передаёт B подписанный лог challenge-response с пиром C. B проверяет подписи и вычисляет trust из чужих наблюдений.

**Защита от одностороннего обмана** (A скрывает провалы без ведома C):

Три крипто-примитива делают selective disclosure детектируемым:

1. **Детерминированное расписание.** Расписание проверок вычисляется из публичных ключей:
   `should_check(A, C, week) = H(A_pub || C_pub || week) mod N < threshold`.
   Пропущенная неделя — видна любому, расписание неподделываемо.

2. **Hash chain.** Каждая запись содержит `prev_hash` → удаление записи рвёт цепочку.

3. **Периодические commitments.** Раз в месяц нода публикует в gossip `{peer, month, total_checks, chain_head, signature}`. Переписать историю нельзя — commitment уже у десятков нод.

**Фундаментальное ограничение: сговор A+C.**

A знает свои данные и может вычислить любой шард. При сговоре A отправляет C правильный ответ в реальном времени → challenge-response проходит, хотя C ничего не хранит. Все подписи валидны, hash chain целый, расписание совпадает. Криптографически неотличимо от честного лога.

Единственный крипто-примитив, закрывающий сговор — Proof of Replication (Filecoin): уникальная sealed-копия, sealing стоит часы GPU-работы. Нереально для домашних пользователей.

**Почему сговор не опасен — архитектурная защита:**

```
B доверился C на основании фейкового referral от A.
B разложил данные 5-of-15, один шард отдал C.

Неделя 1-2: B отправляет собственный challenge ноде C.
  A не может помочь — у A нет данных B (зашифрованы ключом B).
  C не отвечает → trust(C) у B падает.
Неделя 3-4: B заменяет C, делает repair.

Ущерб: 1 шард из 15 "висит" 2 недели. Данные в безопасности.
ROI сговора отрицательный: месяцы инвестиций → 2 недели × 1 шард.
```

**Вывод: referral — ускоритель bootstrap, не механизм доверия.**

| Защита от | Crypto | Архитектура |
|-----------|:---:|:---:|
| A скрывает провалы (односторонне) | **да** (chain + schedule) | — |
| A+C сговор (фейковый referral) | **нет** | **да** — ущерб 1/15 на 2 нед |
| C реально не хранит | — | **да** — B обнаруживает за 1-2 нед |

Ограничения referral trust:
- `max_referral_I = 0.3` — хватает для acceptance gate, не для полного доверия
- Referral decay: 2 месяца, замещается собственными наблюдениями
- Требовать evidence от ≥3 независимых нод (конфликт = максимальный discount)

### Внутри Personal Cluster

Устройства одного пользователя (ноутбук, NAS, десктоп) = один identity с общим master key. Trust shared полностью (discount = 1.0). Это не "referral" — это одна сущность на нескольких устройствах.

## 6. Адаптивная избыточность: используй всех, управляй риском

### Смена парадигмы

Серия 1-2 строилась на логике "фильтруй плохих": acceptance gate, eviction, trust escrow — всё это механизмы **отсечения**. Низкий trust → не даём хранить / не даём забрать / выгоняем.

Но это создаёт замкнутый круг для новичков и неоптимально для сети. Альтернатива:

**Низкий trust ≠ бесполезен. Низкий trust = ненадёжен → компенсируем избыточностью.**

### Механика

Количество шардов n для файла зависит не только от типа данных, но и от надёжности партнёров:

```
target_reliability = 99.99%
k = min_shards_to_restore (зависит от типа данных)
n = f(k, partner_trusts, target_reliability)

Примеры (k=5):
  Все партнёры reliable (trust ≈ 2.5): n = 12 → overhead 2.4x
  Микс reliable + newcomers (avg ≈ 1.5): n = 18 → overhead 3.6x
  Много ненадёжных (avg ≈ 0.8): n = 25 → overhead 5.0x
```

Overhead пропорционален риску. Сеть автоматически тратит больше на страховку когда среда ненадёжная, и меньше — когда стабильная.

### Bootstrap без проблем

```
Newcomer приходит, trust = 0, S = 0.
→ Другие дают ему шарды как "запасные копии" (extra redundancy)
→ Если уйдёт — ничего не потеряно (основные копии у надёжных)
→ Если останется — шард становится "основной копией"
→ S растёт (реально хранит!), trust растёт, overhead снижается
```

Нет acceptance gate. Нет периода ожидания. Новичок полезен с первой минуты — его вклад просто "дешёвый" (ненадёжный, компенсируется копиями).

### Hoarder/Freeloader — не паразиты, а ненадёжные помощники

```
Hoarder хранит 20% от потребляемого → trust низкий →
  система кладёт на него "дешёвые" шарды (extra copies)
  → если потеряет — не страшно (основные копии целы)
  → если не потеряет — его 20% реально помогают снизить нагрузку на остальных
```

Hoarder не "паразит, которого надо выгнать". Hoarder — "ненадёжный помощник, которого используем с поправкой на риск".

### Eviction — экономический, не бинарный

Нет порога "trust < X → выгнать". Вместо этого:

```
Диск заполнен, нужно место →
  Выгнать шард с минимальным (trust_партнёра × важность_файла) →
  Заменить на шард для более надёжного партнёра / важного файла
```

Eviction происходит только при давлении на ресурсы, не по правилу. Ненадёжный партнёр вытесняется последним, когда место нужнее.

### Связь с trust escrow

Escrow сохраняется как механизм **кредитования**, а не отсечения:

- Upload всегда разрешён (данные в сети — "дешёвые" копии на ненадёжных пирах)
- Restore: первый 1 ГБ бесплатно (демо-кредит), дальше — пропорционально I-score
- Escrow — это не "не дадим забрать", а "сначала покажи, что ты часть системы"
- Lock-in: файлы в безопасности, доступ растёт с репутацией — мощная мотивация остаться

Escrow + адаптивная избыточность: файлы новичка хранятся как extra copies (дёшево для сети), доступ к restore — по I-score (мотивация вносить вклад).

### Что становится необязательным

| Механизм | При фильтрации | При адаптивной избыточности |
|-----------|:---:|:---:|
| Acceptance gate | Обязателен (не дать новичку хранить) | Не нужен (новичок хранит "дешёвые" копии) |
| Мультипликативный S | Нужен (чтобы Hoarder не получал высокий trust) | Менее критичен (ошибка ранжирования компенсируется extra copies) |
| Hard eviction | Нужен (чтобы убрать плохих партнёров) | Мягкий (экономический, при давлении на диск) |
| Trust escrow | Защита экономики | Кредитование + мотивация (сохраняется, меняется смысл) |

### Что остаётся обязательным

- PI+S формула: нужна для определения n (сколько шардов)
- Proof-of-storage: нужен для верификации
- Subnet rate-limiting: нужен против Sybil
- Erasure coding: основа всей системы

## 7. Gossip relay: каждая нода — почтальон

### Проблема dedicated relay

RESEARCH.md (раздел 4.7) описывает relay как выделенный сервер-почтальон для асинхронного challenge-response. Но это создаёт точку централизации, требует инфраструктуру, и плохо масштабируется (1000 пиров × 257 КБ/нед = 250 ГБ relay-трафика).

### Решение: epidemic routing

Dedicated relay не нужен. Каждая нода хранит "почту" для своих соседей и пересылает при встрече:

```
A (online пн) → challenge → C, D, E (кто сейчас подключён)
C (online вт) видит D, F → пересылает им копию
D (online ср) видит B → доставляет challenge
B → response → D → ... → A

Цепочка: 2-4 hops, 1-4 дня. Дедлайн = 7 дней.
```

### Overhead на ноду

```
Хранение почты: ~20-30 соседей × 257 КБ = 5-8 МБ (max)
TTL: 7 дней → мусор самоочищается
Rate limit: 1 msg/peer/week → спам невозможен
Сообщения подписаны → подделка невозможна
```

Нагрузка распределяется пропорционально uptime: кто чаще онлайн — больше пересылает. Это справедливо и автоматически.

### Устойчивость к потере сообщений

Gossip вносит потери и задержки. Ключевой вопрос: как это влияет на trust?

```
Ежедневные проверки + недельная агрегация (≥1 OK → weekly_score = 1):
  При loss rate 10%: P(miss entire week) = 0.1^7 ≈ 0.0000001
  При loss rate 30%: P(miss entire week) = 0.3^7 ≈ 0.0002

Одна проверка в неделю:
  При loss rate 10%: P(miss) = 10% — каждая десятая неделя ложно штрафуется
```

Ежедневные проверки с недельной агрегацией делают систему **практически неуязвимой** к потере сообщений. Overhead: ~13 МБ/нед на 100 ГБ данных (~1.8 МБ/день). Компромисс: 2-3 проверки/неделю = 99%+ устойчивость при 3x меньшем bandwidth.

### Когда dedicated relay всё-таки нужен

1. **Bootstrap**: первый контакт с сетью (аналог DNS seed в Bitcoin). 1-2 hardcoded адреса.
2. **NAT traversal**: QUIC hole punching ~70%, остальное — STUN/TURN для установления соединения (секунды, не данные).

Оба случая — точечные, не постоянный relay-трафик.
