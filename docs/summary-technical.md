# SyncBack: технический обзор для студентов IT

*Март 2026 · v0.1*

---

## 1. Задача и мотивация

Личные данные обычного человека (документы, фото — 30-160 ГБ) не защищены от потери. Облачные сервисы требуют постоянной оплаты и доверия третьей стороне, второй диск требует денег и дисциплины, NAS требует экспертизы. SyncBack решает задачу иначе: участники сети хранят зашифрованные фрагменты данных друг друга, не платя за инфраструктуру и не зная содержимого чужих файлов.

Ключевой тезис: erasure coding, шифрование, P2P-транспорт — всё это решённые задачи с production-grade библиотеками. **Единственная нерешённая проблема — механизм доверия:** как незнакомцы договариваются хранить данные друг друга без посредника, токенов и глобального консенсуса. За 23 года после Samsara (2003) этот механизм так никто и не реализовал в production.

Концепция "холодного бекапа" (временная константа = 1 неделя вместо минут) радикально упрощает все остальные проблемы: churn, repair storm, NAT traversal, требования к uptime — всё решается фразой "попробуй позже".

## 2. Архитектура

### PI-контроллер доверия

Каждый пир локально считает репутацию своих партнёров по аналогии с PID-контроллером теории управления:

```
Trust = 0.5 × P_30d + 2.0 × I_cumulative

P = доля успешных proof-of-storage проверок за последние 30 дней
I = Σ(GB × days) за всё время — накопленная история хранения
D = тренд P за 30 дней — используется только для раннего обнаружения деградации
```

Ключевой инсайт: **время неподделываемо**. Пир с историей 2 года × 10 ГБ = 7300 ГБ·дней не может ускорить этот факт. Это лучший anti-Sybil механизм без блокчейна — честная работа в течение двух лет стоит дороже, чем данные, которые атакующий мог бы уничтожить.

Нет глобального консенсуса: каждый пир ведёт собственный локальный лог событий и самостоятельно принимает решения о доверии.

### Erasure coding и tiered data model

Файлы не реплицируются целиком — они разбиваются на шарды по схеме k-of-n (Reed-Solomon и аналоги). Чтобы восстановить файл, достаточно любых k шардов из n.

```
Tier 1: Документы → 5-of-15 (допускает потерю 10 из 15 шардов) → overhead ~3x
Tier 2: Фото      → 4-of-10 (допускает потерю 6 из 10 шардов)  → overhead ~2.5x
Tier 3: Видео     → 6-of-10 (допускает потерю 4 из 10 шардов)  → overhead ~1.7x
```

Пример: пользователь с 100 ГБ данных занимает ~15 ГБ на каждом из 15 партнёров. Это реально для устройств со 200-500 ГБ свободного места.

### Personal Cluster

Пользователь — не одна нода, а кластер доверенных устройств с общим master key:

```
Identity (seed phrase)
├── Laptop    (device key 1, derived)
├── Desktop   (device key 2, derived)
├── NAS       (device key 3, derived)
└── Trusted partner (device key 4, delegated, revocable)
```

Внутри кластера — нет верификации, мгновенный restore, общая репутация. Между кластерами — полный протокол доверия. Аналогия: "семья" против "деревни" в экономике Грейбера.

### Subnet rate-limiting

Ключевая защита от Sybil-атак: не более одного шарда одного файла на пиры из одной /24-подсети. Это ограничивает максимальное количество шардов, которые атакующий может разместить у себя, даже запустив тысячи нод — они все окажутся в одной подсети. Плюс: не более 2 шардов из одного ASN, не более 1 шарда от пиров, присоединившихся в один день.

### Асинхронная верификация через "почтальонов"

Два пира могут никогда не быть online одновременно. Proof-of-storage реализован как асинхронный challenge-response через relay-ноды:

1. Пир A создаёт challenge `{nonce, block_index, signed_by: A}` и кладёт в gossip/DHT.
2. Пир B (другое время суток) подбирает challenge, отвечает `{block_data, merkle_proof, signed_by: B}`.
3. Пир A при следующем выходе online проверяет подпись и Merkle proof против сохранённого root.

Relay-нода не может подделать результат — ответ подписан private key хранителя. Стоимость одного цикла верификации: ~2.5 МБ/неделю на 10 шардов.

## 3. Ключевые design decisions

**Почему PI, а не blockchain.** Blockchain требует глобального консенсуса и привлекает спекулянтов (Autonomi / MaidSafe за 20 лет не смогли). PI-репутация считается локально, не требует токенов, использует время как неподделываемый ресурс. Предшественники с токенами (Autonomi) привлекли фармеров, а не пользователей; нода с 35 ГБ за 3 недели работы заработала 0 токенов.

**Почему GB·days, а не GB.** Просто "сколько хранит сейчас" легко симулировать новой нодой. GB·days нельзя ускорить — это физические байты на диске умноженные на реальное время. I-компонент доминирует в формуле (Ki=2.0 против Kp=0.5), потому что накопленная история надёжнее текущего состояния.

**Почему D не входит в trust score, но используется для repair.** Эксперимент 1 показал: D ухудшает ранжирование (Kendall's tau). Эксперимент 3 показал: D даёт +30% выживаемости данных при медленном repair. Вывод: D — это early warning для _триггера repair_, а не компонент _оценки пира_. Разные роли для разных компонентов.

**Почему холодный бекап, а не real-time sync.** Wuala, CrashPlan, BuddyBackup все пытались конкурировать с AWS по SLA и проиграли. "Холодный бекап" убирает несколько классов проблем одновременно: repair storm становится "лёгким ветром" (160 ГБ за 7 дней = 260 КБ/с), churn перестаёт быть проблемой (offline 3 дня = ноутбук закрыт, подождём), NAT failures решаются retry (за неделю — десятки попыток).

**Почему 5-of-15, а не 3-of-5.** Более широкое кодирование (больше шардов, больше "лишних") обеспечивает устойчивость к концентрации атакующих нод. С 5-of-15 нужно сломать 11 из 15 шардов — практически невозможно при случайном распределении. Стоимость: ~3x overhead на storage вместо ~2x. Это "налог на безопасность", который окупается во всех протестированных сценариях атак.

**Почему нет токенов.** Autonomi (ex-MaidSafe, 20 лет разработки) закрылся в марте 2026: токен-эмиссия привлекла farming-ноды, их уход вызвал repair storm. GB·days как "валюта" и репутация как "кредитный лимит" — по аналогии с долговой экономикой Грейбера — позволяют участникам, которым нужно хранить данные, взаимодействовать напрямую без финансовых инструментов.

## 5. Главный вывод: почему 5-of-15

Схема 5-of-15 (5 шардов достаточно для восстановления, всего 15) является рекомендуемым дефолтом для критичных данных. Эксперименты объясняют почему:

- **Sybil (Exp 04):** 6-of-10 уязвим при масштабной атаке (58.9% потерь), 5-of-15 практически невосприимчив (3.15%).
- **Spite (Exp 07):** 5-of-15 даёт нулевые потери во всех конфигурациях, 7-of-10 — до 7.35%.
- **Mass departure (Exp 06):** 5-of-15 переживает мгновенный уход 20% сети с нулевыми потерями; 7-of-10 теряет 12% файлов при тех же условиях.
- **Storage lying (Exp 08):** 5-of-15 устойчив к 20% лжецов в сети; для потери файла нужно 11+ шардов у лжецов — вероятность ~10⁻⁸ при случайном распределении.

Стоимость схемы: ~3x storage overhead против ~1.7x для 6-of-10. Ценность: иммунитет к практически всем рассмотренным атакам.

## 6. Обнаруженные проблемы дизайна

**Storage fairness (Exp 13):** PI-контроллер измеряет только uptime (проходимость proof-of-storage проверок), но не объём хранимых данных. Hoarder с 90% uptime и 20% ёмкости получает trust #2 из 6 — выше, чем Weekend Warrior, который реально полезнее. Необходим дополнительный term в формуле: `storage_balance = GB_stored_for_others / GB_stored_by_others`. Это расширение PI-контроллера до PI+SB (storage balance).

**D-component в UX (Exp 14):** D-warnings генерируют ~55 событий/год при 91% false positive rate. Прямое отображение D-warnings пользователю создаёт "alarm fatigue". Рекомендация: D использовать только для автоматического repair trigger (подтверждено в Exp 03), в UX показывать только restore probability и trend доверия.

**Weekend Warrior penalty (Exp 13):** Ежедневные проверки несправедливо штрафуют пиров с периодическим, но предсказуемым расписанием. Возможное решение: недельный цикл проверки вместо дневного, или P-window в неделях.

## 7. Открытые вопросы и следующие шаги

**Нерешённые вопросы протокола:**
- Конкретный формат gossip-протокола для асинхронных challenge-response
- Bootstrap relay: как новый пользователь находит первых партнёров без DHT-истории?
- Metadata consistency при одновременном изменении файлов с нескольких устройств Personal Cluster
- Storage-balance term: конкретная формула и веса для PI+SB контроллера
- Минимальный жизнеспособный размер сети: 7 (10% churn) или 20 (25% churn) — подтверждено Exp 12

**Следующий шаг:** reference implementation протокола (Python/Go), затем RFC-style спецификация.
